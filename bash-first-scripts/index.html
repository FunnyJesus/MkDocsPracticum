    Bash: первые полезные скрипты

    Лестница из 10 маленьких скриптов, которые реально нужны в работе. Каждый следующий добавляет один-два новых приёма к уже знакомым. Не перескакивай: третий скрипт строится на первых двух.

    Справка по синтаксису — Bash-скрипты и шпаргалка. Большой скрипт со всеми «а что, если…» — задача 18 в Практических заданиях.

    Где запускать

    Скрипты пишутся для Linux-серверов. На macOS часть команд другая (free, uptime -p, /proc, ключи date и find), поэтому запускай в контейнере Ubuntu:

    mkdir -p ~/bash-lab && cd ~/bash-lab
docker run -it --rm -v "$PWD":/w -w /w ubuntu:24.04 bash
apt-get update -qq && apt-get install -y -qq curl procps shellcheck   # внутри контейнера, один раз

    Файлы в ~/bash-lab видны и на Mac (редактор), и в контейнере (запуск).

    Каждый скрипт:

    chmod +x имя.sh      # сделать исполняемым
./имя.sh             # запустить
shellcheck имя.sh    # линтер: подсказывает кавычки, read -r и другие ошибки новичка

    Как работать: сначала напиши сам, проверь, прогони shellcheck, и только потом открывай решение. Подсказка — если застрял дольше 15 минут. Эти же задания выдаёт бот-тренажёр (/task) и возвращает их на повтор — тогда без подсказок.

    Bash: основы

    Задача 1. Сводка о сервере

    Уровень: ★☆☆ · Время: ~15 мин

    Цель. Одной командой узнать, что за машина перед тобой: первое, что делаешь на незнакомом сервере.

    Что потренируешь: подстановку команды $(...), конвейер |, простейший awk.

    Требования. Скрипт sysinfo.sh выводит:

    Хост:     ...
ОС:       Ubuntu 24.04 LTS
Аптайм:   up 3 hours, 12 minutes
Загрузка: 0.15 0.10 0.05 (ядер: 4)
Память:   1.2Gi из 7.7Gi
Диск /:   12G из 59G (21%)
    Подсказка

    hostname, uptime -p, nproc. Название ОС — в файле /etc/os-release, строка PRETTY_NAME="Ubuntu 24.04 LTS": найти её grep, вырезать текст между кавычками — cut -d '"' -f2. Загрузка — первые три числа файла /proc/loadavg. Из free -h и df -h / нужную строку и колонки достаёт awk: awk '/^Mem:/ {print $3}' — третья колонка строки, начинающейся с Mem:.

    Решение 
    #!/usr/bin/env bash
# Сводка о сервере: имя, ОС, аптайм, загрузка, память, диск

echo "Хост:     $(hostname)"
echo "ОС:       $(grep '^PRETTY_NAME=' /etc/os-release | cut -d '"' -f2)"
echo "Аптайм:   $(uptime -p)"
echo "Загрузка: $(cut -d ' ' -f1-3 /proc/loadavg) (ядер: $(nproc))"
echo "Память:   $(free -h | awk '/^Mem:/ {print $3 " из " $2}')"
echo "Диск /:   $(df -h / | awk 'NR==2 {print $3 " из " $2 " (" $5 ")"}')"

    Почему так. $(команда) подставляет вывод команды в строку. cut -d '"' -f2 режет строку по кавычкам и берёт второй кусок — текст внутри них. В awk NR==2 — вторая строка (первая у df — заголовок), $3 — третья колонка.

    Задача 2. Сервис отвечает?

    Уровень: ★☆☆ · Время: ~20 мин

    Цель. Проверить, что сайт или API отвечает 200 — и сообщить об этом кодом выхода, чтобы скрипт можно было использовать в других скриптах и в CI.

    Что потренируешь: аргументы $1, проверку «аргумент не забыли», if, код выхода exit.

    Требования.

    • ./is-up.sh https://ya.ru → OK https://ya.ru, код выхода 0;
    • ./is-up.sh https://ya.ru/no-such-page → FAIL ... (код 404), код выхода 1;
    • без аргумента — понятное сообщение, как запускать;
    • не ждать дольше 5 секунд.

    Проверка.

    ./is-up.sh https://ya.ru; echo "код выхода: $?"
./is-up.sh https://ya.ru/no-such-page; echo "код выхода: $?"
./is-up.sh https://ya.ru && echo "можно деплоить"     # && — только если код 0
    Подсказка

    Код ответа: curl -s -o /dev/null -w '%{http_code}' URL. Многие сайты отвечают не 200, а перенаправлением (301/302 — «иди туда») — ключ -L заставляет curl пройти по нему до конечного ответа. Обязательный аргумент с сообщением: url="${1:?usage: $0 <url>}". $? — код выхода последней команды.

    Решение 
    #!/usr/bin/env bash
# Проверка, что URL отвечает 200. Код выхода: 0 — OK, 1 — нет.

url="${1:?usage: $0 <url>}"

code=$(curl -sL -o /dev/null --max-time 5 -w '%{http_code}' "$url")

if [ "$code" = "200" ]; then
  echo "OK $url"
else
  echo "FAIL $url (код $code)"
  exit 1
fi

    Почему так. -L — без него https://ya.ru даёт 302 (перенаправление) и скрипт сказал бы FAIL про рабочий сайт. Код выхода — главный способ скриптов «разговаривать» друг с другом: 0 — успех, не 0 — ошибка. Именно его смотрят &&, ||, if и CI. "$url" в кавычках — иначе адрес с & или пробелом сломает команду. Если сайт не ответил вовсе, curl выдаст код 000.

    Задача 3. Бэкап каталога с датой в имени

    Уровень: ★☆☆ · Время: ~20 мин

    Цель. Перед рискованным изменением (обновление, правка конфига) — сохранить каталог в архив.

    Что потренируешь: set -euo pipefail, значение по умолчанию ${VAR:-...}, date, tar.

    Требования.

    • ./backup.sh /etc/nginx → архив nginx-20261103-143015.tar.gz;
    • куда класть — переменная BACKUP_DIR, по умолчанию ~/backups (каталог создать, если нет);
    • если каталога-источника нет — скрипт падает, а не создаёт пустой архив;
    • в конце — путь и размер архива.

    Проверка.

    ./backup.sh /etc
BACKUP_DIR=/tmp/bk ./backup.sh /etc/apt
./backup.sh /нет-такого; echo $?                  # не 0
tar -tzf ~/backups/etc-*.tar.gz | head -3        # что внутри
    Подсказка

    date +%Y%m%d-%H%M%S, basename и dirname — имя и родитель пути. tar -czf АРХИВ -C РОДИТЕЛЬ ИМЯ — в архиве будет только ИМЯ/..., без полного пути. Подвох: tar создаёт файл архива до того, как обнаружит, что источника нет, — проверь каталог заранее: [ -d "$src" ].

    Решение 
    #!/usr/bin/env bash
# Бэкап каталога в tar.gz с датой в имени
set -euo pipefail

src="${1:?usage: $0 <каталог>}"
dest="${BACKUP_DIR:-$HOME/backups}"
name="$(basename "$src")-$(date +%Y%m%d-%H%M%S).tar.gz"

if [ ! -d "$src" ]; then
  echo "Нет каталога: $src" >&2
  exit 1
fi

mkdir -p "$dest"
tar -czf "$dest/$name" -C "$(dirname "$src")" "$(basename "$src")"

echo "Бэкап: $dest/$name ($(du -h "$dest/$name" | cut -f1))"

    Почему так. set -euo pipefail — три страховки: -e остановиться на первой ошибке, -u ошибка при обращении к несуществующей переменной (опечатка в имени), -o pipefail — ошибка в середине конвейера не теряется. Ставь в каждый скрипт, который что-то меняет. Но set -e не спасает от последствий: без проверки [ -d ] tar упал бы, успев создать битый архив. Проверяй входные данные до того, как что-то создавать или менять.

    Задача 4. Удалить старые логи — безопасно

    Уровень: ★☆☆ · Время: ~20 мин

    Цель. Диск забит старыми логами. Удалить *.log старше N дней — но сначала показать, что будет удалено, и удалять только с явным флагом.

    Что потренируешь: find с условиями, необязательный аргумент ${3:-}, режим «сухого прогона».

    Требования.

    • ./cleanup.sh /var/log/app 7 — только показать файлы *.log старше 7 дней;
    • ./cleanup.sh /var/log/app 7 --force — удалить их и показать, что удалено;
    • другие файлы и свежие логи не трогать.

    Проверка — сделать тестовые файлы с датой в прошлом:

    mkdir -p /tmp/logs
touch -d '10 days ago' /tmp/logs/old.log
touch -d '10 days ago' /tmp/logs/old.txt
touch /tmp/logs/new.log
./cleanup.sh /tmp/logs 7          # покажет только old.log
./cleanup.sh /tmp/logs 7 --force  # удалит old.log
ls /tmp/logs                      # new.log и old.txt на месте
    Подсказка

    find КАТАЛОГ -type f -name '*.log' -mtime +7 -print — файлы, изменённые больше 7 дней назад. Добавить -delete — удалить. Третий аргумент необязательный: "${3:-}" — пустая строка, если его нет (иначе set -u упадёт).

    Решение 
    #!/usr/bin/env bash
# Удаление *.log старше N дней. Без --force только показывает, что будет удалено.
set -euo pipefail

dir="${1:?usage: $0 <каталог> <дней> [--force]}"
days="${2:?укажи, старше скольких дней удалять}"

if [ "${3:-}" = "--force" ]; then
  find "$dir" -type f -name '*.log' -mtime +"$days" -print -delete
else
  echo "Будут удалены (запусти с --force, чтобы удалить):"
  find "$dir" -type f -name '*.log' -mtime +"$days" -print
fi

    Почему так. Любой скрипт, который удаляет, по умолчанию должен только показывать — опечатка в пути (/ вместо /var/log/app) стоит дорого. '*.log' в одинарных кавычках — чтобы шаблон раскрыл find, а не bash. Удаление по расписанию — через cron или systemd timer.

    Задача 5. Дождаться, пока сервис поднимется

    Уровень: ★★☆ · Время: ~30 мин

    Цель. После деплоя или docker compose up сервис стартует не мгновенно. Скрипт ждёт, пока URL начнёт отвечать, но не дольше таймаута.

    Что потренируешь: цикл until, арифметику $(( )), вывод ошибок в stderr (>&2).

    Требования.

    • ./wait-for.sh http://localhost:8080/health 60 — опрашивать раз в 2 секунды;
    • ответил — ... отвечает, код 0;
    • не ответил за таймаут — сообщение в stderr, код 1;
    • таймаут по умолчанию — 60 секунд.

    Проверка.

    ./wait-for.sh https://ya.ru 10; echo $?               # сразу OK
./wait-for.sh http://localhost:9999 6; echo $?        # ~6 секунд, потом FAIL и 1
# с настоящим сервисом (в другом терминале):
#   sleep 10 && docker run --rm -p 8080:80 nginx:1.27-alpine
./wait-for.sh http://localhost:8080 30
    Подсказка

    until КОМАНДА; do ...; done — повторять, пока команда не завершится успешно. curl -sf возвращает ошибку на ответы 4xx/5xx и на недоступность. Текущее время в секундах — date +%s; срок — $(( $(date +%s) + timeout )).

    Решение 
    #!/usr/bin/env bash
# Ждать, пока URL начнёт отвечать (2xx/3xx). Код 1 — если не дождались за таймаут.
set -euo pipefail

url="${1:?usage: $0 <url> [таймаут_сек]}"
timeout="${2:-60}"
deadline=$(( $(date +%s) + timeout ))

until curl -sf -o /dev/null --max-time 3 "$url"; do
  if [ "$(date +%s)" -ge "$deadline" ]; then
    echo "Не дождался $url за ${timeout}с" >&2
    exit 1
  fi
  echo "ждём $url..."
  sleep 2
done

echo "$url отвечает"

    Почему так. until с командой — частый приём: «повторяй, пока не получится». Без таймаута такой цикл в CI висел бы вечно. Ошибку — в stderr (>&2): тогда ./wait-for.sh ... > log не спрячет её. Так же устроены проверки в CI после деплоя (smoke-тест диплома).

    Bash: файлы и вывод команд

    Задача 6. Проверить список адресов из файла

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Смоук-проверка стенда: пройти по списку адресов и показать, какие отвечают.

    Что потренируешь: чтение файла построчно while read, пропуск пустых строк и комментариев.

    Требования.

    • адреса в urls.txt, по одному в строке; пустые строки и строки с # пропускать;
    • для каждого: OK 200 адрес или FAIL 404 адрес;
    • код выхода 1, если хотя бы один адрес не ответил.
    # urls.txt
https://ya.ru
https://github.com

# сломанный:
https://ya.ru/no-such-page
    Подсказка

    while read -r url; do ...; done < urls.txt. Пропустить строку: [ -z "$url" ] && continue (пустая), [[ "$url" == \#* ]] && continue (комментарий). Флаг «был сбой» — переменная failed=1, в конце exit "$failed".

    Решение 
    #!/usr/bin/env bash
# Проверка списка URL из файла. Код 1 — если хотя бы один не ответил 2xx/3xx.

file="${1:-urls.txt}"
failed=0

while read -r url; do
  [ -z "$url" ] && continue
  [[ "$url" == \#* ]] && continue

  code=$(curl -s -o /dev/null --max-time 5 -w '%{http_code}' "$url")
  if [[ "$code" == 2* || "$code" == 3* ]]; then
    echo "OK   $code $url"
  else
    echo "FAIL $code $url"
    failed=1
  fi
done < "$file"

exit "$failed"

    Почему так. read -r — не превращать \ в спецсимвол (shellcheck подскажет). set -e здесь специально нет: curl к недоступному адресу возвращает ошибку, и code=$(curl ...) с set -e оборвал бы весь скрипт на первом же упавшем сайте (код при этом всё равно 000 — его печатает -w). Полная версия с set -e, || true, ретраями и потерянной последней строкой — задача 18 практических заданий.

    Задача 7. Топ ошибок в логе

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Инцидент: «что вообще сыпется в логе?». Посчитать ошибки и показать самые частые.

    Что потренируешь: grep, sed, классический конвейер sort | uniq -c | sort -rn | head.

    Тестовый лог:

    cat > app.log <<'EOF'
2026-11-03 10:00:01 INFO started
2026-11-03 10:00:02 ERROR db timeout
2026-11-03 10:00:03 ERROR db timeout
2026-11-03 10:00:04 WARN slow request
2026-11-03 10:00:05 ERROR payment declined
2026-11-03 10:00:06 ERROR db timeout
EOF

    Требования.

    Строк с ошибками: 4
Топ повторяющихся ошибок:
      3 ERROR db timeout
      1 ERROR payment declined
    • дата и время в начале строки при подсчёте не учитываются (иначе каждая строка уникальна);
    • если ошибок нет — Строк с ошибками: 0, скрипт не падает.
    Подсказка

    grep -c — число строк. Отрезать дату: sed -E 's/^[0-9-]+ [0-9:]+ //'. Посчитать одинаковые строки: sort | uniq -c, по убыванию — sort -rn, первые 5 — head -5. Подвох: grep без совпадений возвращает код 1, и set -e остановит скрипт.

    Решение 
    #!/usr/bin/env bash
# Число строк с ERROR и топ-5 повторяющихся ошибок (без даты и времени)
set -euo pipefail

log="${1:?usage: $0 <лог-файл>}"

total=$(grep -c 'ERROR' "$log" || true)
echo "Строк с ошибками: $total"

if [ "$total" -gt 0 ]; then
  echo "Топ повторяющихся ошибок:"
  grep 'ERROR' "$log" | sed -E 's/^[0-9-]+ [0-9:]+ //' | sort | uniq -c | sort -rn | head -5
fi

    Почему так. || true — grep -c при нуле совпадений печатает 0, но возвращает код 1; без || true скрипт с set -e упал бы на «хорошем» логе. Конвейер sort | uniq -c | sort -rn — один из самых полезных в работе: так же ищут самые частые IP в логах nginx или самые частые пути запросов.

    Задача 8. Предупреждение о заполнении диска

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Скрипт для cron: проверить все разделы и предупредить, если какой-то заполнен выше порога.

    Что потренируешь: цикл по выводу команды, обрезку символа ${var%\%}, сравнение чисел -ge.

    Требования.

    • ./disk-alert.sh 80 — порог в процентах, по умолчанию 80;
    • для каждого раздела выше порога: ВНИМАНИЕ: / заполнен на 91% (порог 80%), код выхода 1;
    • всё в порядке — Все разделы ниже 80%, код 0.

    Проверка.

    ./disk-alert.sh; echo $?
./disk-alert.sh 1; echo $?      # порог 1% — сработает на любом разделе
    Подсказка

    df -P | awk 'NR>1 && $5 ~ /^[0-9]+%$/ {print $5, $6}' даёт строки вида 21% / (условие $5 ~ ... отсекает служебные разделы, где вместо процента -). Читать их в цикле: while read -r use mount; do ... done < <(команда). Убрать %: ${use%\%}. Сравнение чисел — [ "$use" -ge "$limit" ] (не > — это сравнение строк).

    Решение 
    #!/usr/bin/env bash
# Предупреждение, если раздел заполнен выше порога. Код 1 — есть такие разделы.
set -euo pipefail

limit="${1:-80}"
status=0

while read -r use mount; do
  use="${use%\%}"
  if [ "$use" -ge "$limit" ]; then
    echo "ВНИМАНИЕ: $mount заполнен на $use% (порог $limit%)"
    status=1
  fi
done < <(df -P | awk 'NR>1 && $5 ~ /^[0-9]+%$/ {print $5, $6}')

if [ "$status" -eq 0 ]; then
  echo "Все разделы ниже $limit%"
fi
exit "$status"

    Почему так. < <(команда) — подать вывод команды в цикл. С команда | while ... переменная status менялась бы в подоболочке и снаружи цикла осталась бы 0. df -P — стабильный формат колонок для скриптов; условие в awk пропускает разделы без процента (иначе [ "-" -ge 80 ] сыплет ошибками). Для cron: */15 * * * * /opt/scripts/disk-alert.sh 85 || <уведомление>.

    Bash: Kubernetes

    Нужен кластер — make up в k8s-platform-lab. Скрипты запускай на Mac (там kubectl), не в контейнере.

    Задача 9. Перезапуск деплоймента — с защитой от прода

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Частая просьба: «перезапусти сервис». Скрипт перезапускает Deployment, ждёт готовности и показывает поды — и переспрашивает, если текущий кластер похож на прод.

    Что потренируешь: kubectl в скриптах, read -p (вопрос пользователю), шаблон *prod*.

    Требования.

    • ./restart.sh my-app my-app (deployment, namespace; namespace по умолчанию default);
    • в начале — какой кластер (контекст), namespace и deployment;
    • если в имени контекста есть prod — спросить подтверждение, по умолчанию «нет»;
    • дождаться окончания rollout (не дольше 3 минут) и показать поды.

    Проверка.

    ./restart.sh my-app my-app
kubectl -n my-app get pods          # поды пересозданы, AGE — секунды
    Подсказка

    Текущий контекст: kubectl config current-context. Перезапуск без изменения манифеста: kubectl rollout restart deployment/ИМЯ, ожидание: kubectl rollout status ... --timeout=180s. Вопрос: read -r -p "Точно? [y/N] " answer.

    Решение 
    #!/usr/bin/env bash
# Перезапуск Deployment с ожиданием готовности. На prod-контексте спрашивает подтверждение.
set -euo pipefail

deploy="${1:?usage: $0 <deployment> [namespace]}"
ns="${2:-default}"
ctx=$(kubectl config current-context)

echo "Кластер: $ctx | namespace: $ns | deployment: $deploy"

if [[ "$ctx" == *prod* ]]; then
  read -r -p "Это prod. Точно перезапустить? [y/N] " answer
  if [ "$answer" != "y" ]; then
    echo "Отменено"
    exit 1
  fi
fi

kubectl -n "$ns" rollout restart deployment/"$deploy"
kubectl -n "$ns" rollout status deployment/"$deploy" --timeout=180s
kubectl -n "$ns" get pods -o wide | grep -E "^NAME|^$deploy-"

    Почему так. Самая частая серьёзная ошибка с kubectl — команда не в том кластере. Поэтому скрипт сначала показывает, куда идёт, а на проде переспрашивает. rollout restart меняет аннотацию пода — Deployment пересоздаёт поды по правилам rolling update, без даунтайма.

    Задача 10. Собрать диагностику пода для баг-репорта

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Под падает. Разработчику нужно всё сразу: манифест, describe, логи (и предыдущего запуска), события. Скрипт собирает это в один архив — приложить к задаче.

    Что потренируешь: сбор вывода в файлы, || true для необязательных шагов, 2>&1, архив.

    Требования.

    • ./collect-debug.sh my-app-7d9f... my-app (pod, namespace);
    • в архиве debug-<pod>-<дата>.tar.gz: pod.yaml, describe.txt, logs.txt, logs-previous.txt, events.txt;
    • если предыдущего запуска не было (под не перезапускался) — скрипт не падает;
    • временная папка после архивации удаляется.

    Проверка — на поде, который точно перезапускался:

    kubectl run crash --image=busybox:1.37 -- sh -c "echo boom; exit 1"
sleep 30
./collect-debug.sh crash default
tar -tzf debug-crash-*.tar.gz
kubectl delete pod crash
    Подсказка

    kubectl logs ПОД --previous падает, если перезапусков не было, — допиши || true. Ошибку тоже стоит сохранить в файл: > файл 2>&1. Архив папки: tar -czf папка.tar.gz папка.

    Решение 
    #!/usr/bin/env bash
# Диагностика пода в архив: манифест, describe, логи (и предыдущего запуска), события namespace
set -euo pipefail

pod="${1:?usage: $0 <pod> [namespace]}"
ns="${2:-default}"
out="debug-$pod-$(date +%Y%m%d-%H%M%S)"

mkdir -p "$out"
kubectl -n "$ns" get pod "$pod" -o yaml > "$out/pod.yaml"
kubectl -n "$ns" describe pod "$pod" > "$out/describe.txt"
kubectl -n "$ns" logs "$pod" --all-containers > "$out/logs.txt" 2>&1 || true
kubectl -n "$ns" logs "$pod" --all-containers --previous > "$out/logs-previous.txt" 2>&1 || true
kubectl -n "$ns" get events --sort-by=.lastTimestamp > "$out/events.txt"

tar -czf "$out.tar.gz" "$out"
rm -rf "$out"
echo "Собрано: $out.tar.gz — приложи к баг-репорту"

    Почему так. Логи — || true: их может не быть, и это не повод терять остальное. А get pod и describe — без него: если пода нет (опечатка в имени), архив без них бессмысленен, лучше упасть сразу. 2>&1 — сообщение «previous terminated container not found» тоже информация, пусть будет в файле. Для тестировщика это готовый инструмент: баг-репорт на упавший сервис — одной командой.
