    Облака

    Облако — это чужие сервера, которые арендуются по API вместо покупки железа. В конспекте IaC провайдер Terraform уже настроен на Yandex Cloud — здесь общие концепции, применимые к любому облаку (AWS, GCP, Yandex Cloud, Azure называют одни и те же вещи разными именами).

    Модели обслуживания

    Модель Что даёт провайдер Что делаешь сам Пример
    IaaS (Infrastructure as a Service) Железо, сеть, гипервизор ОС, рантайм, приложение ВМ (EC2, Yandex Compute)
    PaaS (Platform as a Service) + ОС, рантайм, масштабирование Только код и конфигурация Managed Kubernetes, Cloud Functions, RDS
    SaaS (Software as a Service) Всё, включая приложение Только использование Google Docs, Gmail

    Модель разделённой ответственности (Shared Responsibility)

    Провайдер отвечает за безопасность облака (железо, гипервизор, сеть ЦОД). Ты отвечаешь за безопасность в облаке (конфигурация ОС, права доступа, патчи приложения, security groups).

    Чем выше уровень абстракции (IaaS → PaaS → SaaS), тем больше ответственности переходит провайдеру — но полностью она не исчезает никогда (неправильно настроенный публичный bucket — забота клиента, даже в managed-сервисе).

    Концепция AWS Yandex Cloud GCP Назначение
    Виртуальная машина EC2 Compute Cloud Compute Engine арендуемый сервер
    Объектное хранилище S3 Object Storage Cloud Storage файлы/бэкапы/статика, доступ по HTTP
    Виртуальная сеть VPC VPC VPC изолированная приватная сеть
    Управление доступом IAM IAM IAM кто и что может делать с ресурсами
    Managed база данных RDS Managed Service for PostgreSQL/MySQL Cloud SQL БД без ручного администрирования
    Managed Kubernetes EKS Managed Service for Kubernetes GKE кластер без ручной установки control plane
    Балансировщик ELB/ALB Network Load Balancer / L7 Balancer Cloud Load Balancing распределение трафика (см. Балансировка нагрузки)
    DNS Route 53 Cloud DNS Cloud DNS управление доменными записями

    IAM (Identity and Access Management)

    Управляет тем, кто (пользователь, сервис, приложение) может делать что с каким ресурсом.

    • Пользователь (user) — человек с логином/паролем или ключом доступа.
    • Сервисный аккаунт (service account) — «пользователь» для приложений/CI/Terraform, без человека за ним.
    • Роль (role) — набор разрешённых действий (viewer, editor, admin, либо кастомная роль на конкретные права).
    • Политика (policy) — привязка роли к пользователю/сервисному аккаунту на конкретном ресурсе.

    Принцип наименьших привилегий (least privilege) — выдавай минимум прав, необходимых для задачи. CI-пайплайну, который только деплоит в один Kubernetes-namespace, не нужны права admin на весь облачный аккаунт. Подробнее — в Безопасность.

    # Yandex Cloud CLI — пример работы с сервисным аккаунтом
yc iam service-account create --name terraform-sa
yc resource-manager folder add-access-binding <folder-id> \
  --role editor \
  --service-account-id <sa-id>

# ключ для аутентификации Terraform от имени сервисного аккаунта
yc iam key create --service-account-id <sa-id> --output key.json

    Сети в облаке (VPC)

    • VPC (Virtual Private Cloud) — изолированная приватная сеть внутри облака, аналог локальной сети в датацентре.
    • Подсеть (subnet) — часть VPC, обычно привязана к зоне доступности (availability zone).
    • Публичная подсеть — ресурсы могут иметь внешний IP, доступны из интернета.
    • Приватная подсеть — только внутренние IP; доступ в интернет наружу — через NAT Gateway, входящего доступа снаружи нет.
    • Security Group — firewall на уровне облака, применяется к конкретным ресурсам (ВМ, балансировщику) — см. Сети: Firewall.
    Интернет
   │
[Load Balancer] ── публичная подсеть
   │
[App VMs] ── приватная подсеть (нет прямого входящего доступа)
   │
[NAT Gateway] ── для исходящих запросов приватных ВМ (обновления, внешние API)
   │
[Managed DB] ── ещё более закрытая подсеть, доступ только от App VMs

    Тот же принцип «наружу торчит только прокси/балансировщик, бэкенды приватны», что и в Сетях Docker Compose — просто на уровне облака вместо Docker-сети.

    Object Storage

    • Bucket — «папка верхнего уровня», у которой обычно глобально уникальное имя.
    • Доступ — по HTTP(S)/S3 API, а не через файловую систему.
    • Класс хранения (storage class) — компромисс цена/скорость доступа: «горячее» хранилище (частый доступ, дороже) vs «холодное»/архивное (дешевле, но доступ дольше и может стоить денег за скачивание).
    • Частое применение в DevOps: бэкапы, terraform state (remote backend), артефакты сборки, статика сайта.
    # terraform: пример backend для state в объектном хранилище (Yandex Object Storage, S3-совместимо)
terraform {
  backend "s3" {
    endpoint   = "storage.yandexcloud.net"
    bucket     = "my-terraform-state"
    region     = "ru-central1"
    key        = "prod/terraform.tfstate"
    skip_region_validation      = true
    skip_credentials_validation = true
  }
}

    Хранить state в объектном хранилище, а не локально — стандартная практика: state доступен всей команде и не теряется при потере ноутбука. Подробнее про state — в IaC.

    Managed vs self-hosted

    Managed-сервис (RDS, Managed K8s) Self-hosted (своя ВМ + Postgres)
    Настройка Минимальная Полная ручная установка и настройка
    Обновления/патчи Провайдер Сам
    Резервное копирование Часто «из коробки» Настраивается вручную
    Контроль Ограничен API провайдера Полный
    Стоимость Обычно дороже за единицу ресурса Дешевле по железу, дороже по времени инженера

    На старте/в небольших командах managed-сервисы почти всегда выгоднее по совокупной стоимости — экономия времени инженера перевешивает переплату за ресурс.

    Частые ошибки

    Симптом Причина Решение
    Bucket «утёк» в публичный доступ Дефолтная/ошибочная ACL/policy на public-read Явно проверять политику доступа, закрывать по умолчанию
    Terraform apply от «слишком мощного» сервисного аккаунта Выдали роль admin вместо точечной Кастомная роль с минимально необходимыми правами
    ВМ в приватной подсети не может скачать обновления Нет NAT Gateway Добавить NAT для исходящего трафика
    Неожиданный счёт за облако Забытые ресурсы (неиспользуемые ВМ/диски/IP) Тегирование ресурсов, регулярный аудит, alerting по бюджету

    Best Practices

    • Least privilege везде — IAM-роли, security groups, доступ к state.
    • Публичное — только то, что обязано быть публичным (балансировщик), остальное — в приватных подсетях.
    • State и секреты — не в git, а в managed-хранилище с ограниченным доступом.
    • Тегируй ресурсы (env=prod, owner=team) — упрощает аудит прав и затрат.
    • Managed-сервисы по умолчанию, self-hosted — только когда есть конкретная причина (контроль, цена в большом масштабе, отсутствие нужного managed-сервиса).
