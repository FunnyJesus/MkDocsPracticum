    Практические задания

    Задания «руками» по темам конспекта: написать Dockerfile, поднять мониторинг, задеплоить в кластер, найти поломку. Всё делается локально и бесплатно — облако не нужно. Эти же задания раз в несколько дней присылает бот-тренажёр.

    Окружение

    Инструмент Зачем Установка (macOS)
    Docker (Desktop или OrbStack) контейнеры, compose brew install --cask orbstack
    kind Kubernetes в Docker brew install kind
    kubectl, helm работа с кластером brew install kubectl helm
    Terraform IaC с провайдером Docker brew install hashicorp/tap/terraform
    hadolint, shellcheck, trivy линтеры и сканер brew install hadolint shellcheck trivy

    Kubernetes-задания (6–13) делаются на проекте k8s-platform-lab и развивают его; остальные — самостоятельные.

    Формат задания: уровень и время → цель → требования → проверка → подсказка и решение под спойлерами. Сначала сделай сам, потом сверяйся.

    Уровни: ★☆☆ — разогрев, ★★☆ — рабочая задача, ★★★ — с подвохом или несколько компонентов.

    Одного раза мало

    Один раз сделанное задание даёт узнавание, а не навык. Бот возвращает сделанное задание на повтор через 21 день и через 60 дней — делай его с нуля, в пустой папке, не открывая подсказку и решение. Получилось трижды — навык закреплён.

    Docker

    Задача 1. Dockerfile для Go-сервиса

    Уровень: ★☆☆ · Время: ~30 мин

    Цель. Собрать минимальный и безопасный образ для Go-сервиса.

    // main.go — go mod init example.com/hello
package main

import (
    "fmt"
    "net/http"
)

func main() {
    http.HandleFunc("/health", func(w http.ResponseWriter, _ *http.Request) { fmt.Fprint(w, "ok") })
    http.HandleFunc("/", func(w http.ResponseWriter, _ *http.Request) { fmt.Fprintln(w, "hello") })
    http.ListenAndServe(":8080", nil)
}

    Требования.

    • multi-stage сборка, итоговый образ меньше 15 МБ;
    • запуск не от root, работает с --read-only;
    • зависимости (go.mod) кэшируются отдельным слоем;
    • hadolint Dockerfile — без замечаний.

    Проверка.

    docker build -t hello:1.0 .
docker images hello:1.0                                  # размер
docker run -d --name hello --read-only -p 8080:8080 hello:1.0
curl localhost:8080/health                               # ok
docker exec hello id 2>&1 || docker inspect hello -f '{{.Config.User}}'   # не root
    Подсказка

    Бинарник Go можно собрать статическим (CGO_ENABLED=0) — тогда ему не нужна даже libc и подойдёт пустой образ scratch. Пользователя в scratch нет — задай его числом.

    Решение 
    FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/hello .

FROM scratch
COPY --from=build /out/hello /hello
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/hello"]

    Почему так. go.mod копируется до кода — при правке кода зависимости не перекачиваются. -s -w убирает отладочную информацию. В scratch нет shell, поэтому docker exec hello id не сработает — пользователя смотри через docker inspect. Если сервису нужны HTTPS-запросы наружу — скопируй CA-сертификаты из build-стадии или возьми gcr.io/distroless/static.

    Задача 2. Dockerfile для Python-сервиса с healthcheck

    Уровень: ★★☆ · Время: ~40 мин

    Цель. Образ для FastAPI-приложения, который быстро пересобирается и сам сообщает о своём здоровье.

    # app.py
from fastapi import FastAPI
app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

    requirements.txt: fastapi==0.115.6 и uvicorn==0.34.0.

    Требования.

    • база python:3.12-slim, без кэша pip в образе;
    • при изменении только app.py слой с pip install не пересобирается;
    • .dockerignore (без .git, __pycache__, .venv);
    • не root; HEALTHCHECK — контейнер становится healthy.

    Проверка.

    docker build -t pyapp:1 .
echo "# change" >> app.py && docker build -t pyapp:2 .   # pip install — CACHED
docker run -d --name pyapp -p 8000:8000 pyapp:2
sleep 15 && docker ps --filter name=pyapp                 # (healthy)
    Подсказка

    В slim-образе нет curl. Для HEALTHCHECK можно использовать сам Python: python -c "import urllib.request; urllib.request.urlopen(...)".

    Решение 
    FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
RUN useradd --system --uid 10001 app
USER app

EXPOSE 8000
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

    Почему так. Порядок слоёв: сначала то, что меняется редко (зависимости), потом код. --host 0.0.0.0 обязателен — по умолчанию uvicorn слушает только 127.0.0.1 внутри контейнера, и снаружи до него не достучаться. В Kubernetes HEALTHCHECK игнорируется — там пробы.

    Задача 3. Исправь плохой Dockerfile

    Уровень: ★★☆ · Время: ~30 мин

    Цель. Найти и исправить всё, что делает образ большим, медленным и небезопасным.

    FROM node:20
COPY . /app
WORKDIR /app
RUN apt-get update
RUN apt-get install -y curl vim
RUN npm install
EXPOSE 3000
CMD npm start

    Требования. Назови не меньше 6 проблем, исправь их и сравни: размер образа и время пересборки после правки одного .js-файла — до и после.

    Проверка.

    docker build -t bad . && docker images bad
time docker build -t good -f Dockerfile.good . && docker images good
hadolint Dockerfile.good
    Подсказка

    Смотри на: базовый образ, порядок COPY, кэш слоёв, лишние пакеты, отдельный apt-get update, npm install vs npm ci, dev-зависимости, пользователя, форму CMD, .dockerignore.

    Решение

    Проблемы: полный node:20 (~1 ГБ); COPY . до установки зависимостей — любая правка кода сбрасывает кэш npm install; apt-get update отдельным слоем (устаревший кэш индекса); vim/curl в проде не нужны; npm install вместо воспроизводимого npm ci; dev-зависимости в образе; запуск от root; shell-форма CMD — npm получает сигналы через sh, плохой graceful shutdown; без .dockerignore в контекст летит node_modules и .git.

    FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY . .
USER node
EXPOSE 3000
CMD ["node", "server.js"]

    .dockerignore: node_modules, .git, *.log, Dockerfile*. Если есть шаг сборки (TypeScript, фронтенд) — multi-stage: собрать в одной стадии, скопировать результат в чистую.

    Задача 4. Prometheus + Grafana + node-exporter

    Уровень: ★★☆ · Время: ~1 ч

    Цель. Поднять стек мониторинга одной командой, без ручной настройки в интерфейсе.

    Требования.

    • compose.yaml: prometheus, grafana, node-exporter;
    • Prometheus собирает метрики с node-exporter и с самого себя, retention 2 дня;
    • источник данных Prometheus в Grafana создаётся provisioning-файлом;
    • данные Prometheus и Grafana переживают docker compose down / up (тома);
    • импортирован дашборд «Node Exporter Full» (ID 1860).

    Проверка.

    docker compose up -d
open http://localhost:9090/targets       # оба таргета UP
open http://localhost:3000               # admin/admin, Connections → Data sources — Prometheus уже есть
    Подсказка

    Сервисы в одной compose-сети видят друг друга по имени: таргет — node-exporter:9100. Grafana читает /etc/grafana/provisioning/datasources/*.yaml при старте.

    Решение 
    # compose.yaml
services:
  prometheus:
    image: prom/prometheus:v3.1.0
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.retention.time=2d
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prom-data:/prometheus
    ports: ["9090:9090"]

  node-exporter:
    image: prom/node-exporter:v1.8.2

  grafana:
    image: grafana/grafana:11.4.0
    volumes:
      - ./grafana/datasources:/etc/grafana/provisioning/datasources:ro
      - grafana-data:/var/lib/grafana
    ports: ["3000:3000"]

volumes:
  prom-data:
  grafana-data:

    # prometheus.yml
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: prometheus
    static_configs: [{ targets: ["localhost:9090"] }]
  - job_name: node
    static_configs: [{ targets: ["node-exporter:9100"] }]

    # grafana/datasources/prometheus.yaml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    url: http://prometheus:9090
    isDefault: true

    Дашборд: Dashboards → New → Import → 1860 → источник Prometheus. На macOS node-exporter показывает метрики Linux-ВМ Docker, а не самого Mac — это нормально.

    Задача 5. Nginx как балансировщик перед репликами

    Уровень: ★★☆ · Время: ~40 мин

    Цель. Две реплики сервиса за Nginx, видно, что запросы распределяются.

    Требования.

    • сервис app на образе traefik/whoami (в ответе — имя контейнера), 2 реплики;
    • nginx слушает localhost:8080 и проксирует в app;
    • наружу открыт только Nginx;
    • Nginx передаёт X-Real-IP и X-Forwarded-For.

    Проверка.

    docker compose up -d
for i in 1 2 3 4; do curl -s localhost:8080 | grep Hostname; done   # имена чередуются
    Подсказка

    deploy.replicas в compose создаёт несколько контейнеров с одним DNS-именем. Встроенный DNS Docker отдаёт все их IP, а Nginx при старте добавит каждый адрес в upstream.

    Решение 
    # compose.yaml
services:
  app:
    image: traefik/whoami:v1.10
    deploy:
      replicas: 2
  nginx:
    image: nginx:1.27-alpine
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    ports: ["8080:80"]
    depends_on: [app]

    # nginx.conf
upstream app {
    server app:80;
}
server {
    listen 80;
    location / {
        proxy_pass http://app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

    Подвох. Nginx резолвит app один раз при старте. Масштабируешь docker compose up -d --scale app=3 — Nginx про новую реплику не узнает, пока не сделать docker compose restart nginx. В проде для динамики используют resolver + переменную в proxy_pass или балансировщик с service discovery.

    Kubernetes: k8s-platform-lab

    Задания по Kubernetes делаются на твоём проекте k8s-platform-lab: каждое — доработка проекта, которая остаётся в репозитории и в портфолио. Имена в проекте: кластер kind platform-lab, namespace, релиз и Service — my-app, чарт charts/my-app; эндпоинты приложения — /healthz, /readyz, /metrics, /api/work?ms=N, /admin/ready.

    Перед каждым заданием:

    cd ~/Documents/my_repo/k8s-platform-lab
git switch main && git pull
git switch -c task/<номер>-<кратко>
make up                     # кластер, ingress, metrics-server, деплой; уже поднят — не пересоздаёт

    После: make lint && make test, коммит, pull request в main — CI прогонит e2e на живом kind.

    Повтор задания по проекту. После merge решение уже лежит в main, поэтому «с нуля» — значит в ветке от состояния до задания. Ветка-тренажёр в main не вливается:

    git log --oneline --merges | grep "task/7"      # merge-коммит задания 7
git switch -c repeat/7 <merge-коммит>^1         # ^1 — первый родитель: main до вливания
make down && make up                            # кластер в состоянии «до»
# ...делаешь задание без подсказок...
git diff main -- charts/ Makefile               # сравни с первым решением
git switch main && git branch -D repeat/7

    Для Практикума Helm проще — пересоздать копию чарта: rm -rf charts/app && cp -r charts/my-app charts/app.

    Задача 6. Разбери make up и добавь make status

    Уровень: ★☆☆ · Время: ~30 мин

    Цель. Понимать каждую строку своего Makefile и иметь одну команду для диагностики.

    Требования.

    • Ответить (в описании PR) на вопросы:
      1. Почему deploy зависит от build, а build — от cluster? Что будет при make deploy на пустой машине?
      2. Зачем kind export kubeconfig в цели cluster и в отдельной цели kubeconfig?
      3. Зачем цель ingress патчит контроллер nodeSelector: ingress-ready? Что сломается без патча?
      4. Зачем в начале цели ingress удаляются Job'ы admission-webhook?
      5. Что делают --wait --timeout 5m в deploy и что будет, если поды не станут Ready?
    • Добавить цель make status: ноды, ресурсы релиза с узлами, последние 10 событий namespace, история Helm. Цель видна в make help.

    Проверка.

    make help | grep status
make status
    Подсказка

    Ответы на 3 и 2 есть в README («Честные ограничения»). Для 4: какие поля Job можно менять после создания?

    Решение 
    status: ## состояние кластера и релиза
    kubectl get nodes -o wide
    kubectl -n $(NS) get deploy,pods,hpa,pdb,ingress -o wide
    kubectl -n $(NS) get events --sort-by=.lastTimestamp | tail -10

    И status — в .PHONY. Отступ в рецептах Makefile — табуляция, не пробелы.

    1. Цепочка гарантирует порядок: образ собирается, когда кластер есть, и загружается в него (kind load), а чарт ставится, когда образ уже в кластере. На пустой машине make deploy сам создаст кластер и соберёт образ — но без ingress и metrics-server (их ставит только up).
    2. kind пишет адрес API-сервера с портом Docker, который меняется после перезапуска Docker — старый kubeconfig перестаёт работать.
    3. Порты 80/443 проброшены extraPortMappings только на control-plane. Уедет контроллер на воркер — localhost перестанет отвечать.
    4. spec.template у Job неизменяем: повторный kubectl apply манифеста другой версии упадёт с field is immutable. Удаление делает цель повторяемой.
    5. Helm ждёт готовности ресурсов; не дождался за 5 минут — команда падает, но релиз остаётся в состоянии failed с новыми подами, отката нет (см. задачу 10).

admin:

{{- if and .Values.admin.token (not .Values.admin.existingSecret) }}

  name: {{ include "my-app.fullname" . }}-admin
  labels:
    {{- include "my-app.labels" . | nindent 4 }}

{{- end }}

            checksum/admin: {{ .Values.admin.token | sha256sum }}

    Задача 11. HPA: проверь утверждение README

    Уровень: ★★★ · Время: ~1 ч

    Цель. Как тестировщик: README утверждает, что потолок автоскейлинга — 4 реплики из-за nodeTaintsPolicy, а в CI — 2. Проверь это экспериментом и приведи README в соответствие с реальностью.

    Требования.

    • найди в values.yaml, какое nodeTaintsPolicy стоит на самом деле, и предскажи результат;
    • подними autoscaling.maxReplicas до 8 и дай нагрузку;
    • посчитай поды по узлам, найди Pending (если есть) и их причину;
    • исправь README (или values) так, чтобы описание совпадало с поведением.

    Проверка.

    make deploy HELM_EXTRA="--set autoscaling.maxReplicas=8"    # HELM_EXTRA — из задачи 8
BASE_URL=http://localhost ./scripts/generate-load.sh 180 16
kubectl -n my-app get hpa -w
kubectl -n my-app get pods -l app.kubernetes.io/name=my-app \
  -o custom-columns=NODE:.spec.nodeName,STATUS:.status.phase --no-headers | sort | uniq -c
    Подсказка

    С Ignore узел control-plane — домен распределения, хотя поды на него не попадают из-за taint; с Honor узлы с непереносимыми taint из расчёта исключаются. Посчитай maxSkew для обоих случаев.

    Решение

    В values.yaml стоит nodeTaintsPolicy: Honor (добавлено коммитом «nodeTaintsPolicy в топологию»), а README описывает поведение Ignore:

    • Ignore: домены — control-plane (всегда 0 подов) и два воркера; maxSkew: 2 → на воркере не больше 0 + 2 = 2 пода → потолок 4. В CI (control-plane + 1 воркер) → 2.
    • Honor: control-plane не считается; домены — только воркеры, и распределение ограничивает лишь разницу между ними (5/3, 4/4…). Потолок — autoscaling.maxReplicas и свободный CPU узлов (requests.cpu: 100m на под). В CI единственный воркер — единственный домен, ограничения нет.

    Значит, раздел «Честные ограничения» устарел: пункты про «потолок 4» и «в CI две реплики» нужно переписать (или вернуть Ignore, если ограничение было намеренным). Сколько реплик поднимет HPA, зависит от нагрузки и того, сколько CPU отдано Docker — запиши свои цифры в README.

    Уровень: ★★★ · Время: ~2 ч

    Дашборд писался под compose: проверь, какой job в его запросах и какой будет в кластере. И помни, что {{ }} в шаблонах Prometheus Helm тоже попытается выполнить.

    Решение 
    monitoring: ## Prometheus + Grafana в кластере
    helm repo add prometheus-community https://prometheus-community.github.io/helm-charts --force-update
    helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
        --namespace monitoring --create-namespace --wait --timeout 10m \

        --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false \

    ...NilUsesHelmValues=false — иначе Prometheus берёт только ServiceMonitor и правила с меткой своего релиза. Порядок: сначала make monitoring (ставит CRD), потом make deploy.

    # templates/servicemonitor.yaml
{{- if .Capabilities.APIVersions.Has "monitoring.coreos.com/v1/ServiceMonitor" }}
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}
spec:
  selector:
    matchLabels:
      {{- include "my-app.selectorLabels" . | nindent 6 }}
  endpoints:
    - port: http
      path: /metrics
      interval: 15s
{{- end }}

    # templates/prometheusrule.yaml
{{- if .Capabilities.APIVersions.Has "monitoring.coreos.com/v1/PrometheusRule" }}
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}
spec:
  groups:
    - name: {{ include "my-app.fullname" . }}.slo
      rules:
        - alert: AppLatencySLOBreach
          expr: |
            histogram_quantile(0.95, sum by (le) (rate(
              http_request_duration_seconds_bucket{namespace="{{ .Release.Namespace }}", path=~"/api/.*"}[5m]
            ))) > 0.2
          for: 5m
          labels: { severity: warning }
          annotations:
            summary: "p95 /api/* выше 200 мс — SLO нарушен"
        - alert: AppNoReadyInstances
          expr: sum(app_ready{namespace="{{ .Release.Namespace }}"}) < 1
          for: 1m
          labels: { severity: critical }
          annotations:
            summary: "нет ни одного готового инстанса"
{{- end }}

    Ловушки:

    • Шаблоны Prometheus вида {{ $labels.instance }} внутри чарта Helm выполнит сам и упадёт — экранируй: {{ "{{" }} $labels.instance {{ "}}" }}. В решении выше их нет специально.
    • С NetworkPolicy из задачи 9 разреши вход из namespace monitoring на порт http.

    Grafana: kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80, пароль — kubectl -n monitoring get secret kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | base64 -d. Стек тяжёлый: дай Docker не меньше 6 ГБ памяти.

    Требования.

    • образ nginx:1.27-alpine и контейнер tf-web, внешний порт — переменная (по умолчанию 8081);
    • output с URL;
    • terraform state list, terraform state show для контейнера;
    • поменять порт и посмотреть в plan: обновление на месте или пересоздание?
    Подсказка

    Если registry.terraform.io недоступен — зеркало Yandex Cloud (см. Диплом: Terraform).

    Решение 
    terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker", version = "~> 3.0" }
  }
}

provider "docker" {}

variable "port" {
  type    = number
  default = 8081
}

resource "docker_image" "nginx" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

resource "docker_container" "web" {
  name  = "tf-web"
  image = docker_image.nginx.image_id
  ports {
    internal = 80
    external = var.port
  }
}

output "url" {
  value = "http://localhost:${var.port}"
}

    Смена порта — -/+ must be replaced: порты контейнера нельзя поменять на лету, Terraform пересоздаёт ресурс. Всегда читай в plan символы ~ (на месте) и -/+ (пересоздание) — для БД или кластера это разница между «поменяли настройку» и «потеряли данные».

    Задача 15. Модуль и for_each

    Уровень: ★★☆ · Время: ~45 мин

    Цель. Вынести контейнер из задачи 14 в модуль и создать три экземпляра.

    Требования.

    • модуль modules/web с переменными name, port, output url;
    • в корне — for_each по карте { a = 8081, b = 8082, c = 8083 };
    • output — карта всех URL;
    • удалить b из карты: plan должен удалить только b;
    • объяснить, что было бы с count.
    Решение 
    # modules/web/main.tf
terraform {
  required_providers { docker = { source = "kreuzwerker/docker" } }
}
variable "name" { type = string }
variable "port" { type = number }

resource "docker_container" "this" {
  name  = var.name
  image = "nginx:1.27-alpine"
  ports {
    internal = 80
    external = var.port
  }
}
output "url" { value = "http://localhost:${var.port}" }

    # main.tf
locals { sites = { a = 8081, b = 8082, c = 8083 } }

module "web" {
  source   = "./modules/web"
  for_each = local.sites
  name     = "web-${each.key}"
  port     = each.value
}

output "urls" { value = { for k, m in module.web : k => m.url } }

    С for_each адреса ресурсов — module.web["a"], удаление b трогает только его. С count адреса — индексы [0] [1] [2]: удалишь средний — [2] станет [1], и Terraform пересоздаст «сдвинувшиеся» ресурсы. Поэтому для именованных сущностей — for_each.

    Задача 16. GitHub Actions: тесты и образ по тегу

    Уровень: ★★☆ · Время: ~1 ч

    Цель. Пайплайн для сервиса из задачи 1: проверки на каждый push, образ в GHCR — только на тег.

    Требования.

    • на push и pull request: go vet, go test -race;
    • на тег v*: сборка и push в ghcr.io/<user>/<repo>:<версия без v>;
    • без личных токенов — только GITHUB_TOKEN;
    • кэш слоёв Docker между запусками.
    Решение 
    # .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: "1.25" }
      - run: go vet ./...
      - run: go test -race ./...

  image:
    if: startsWith(github.ref, 'refs/tags/v')
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: v
        run: echo "version=${GITHUB_REF_NAME#v}" >> "$GITHUB_OUTPUT"
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ steps.v.outputs.version }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

    permissions: packages: write нужен, чтобы GITHUB_TOKEN мог писать в GHCR. Имя репозитория в GHCR должно быть в нижнем регистре. Сравни с CI диплома: там build once — образ на тег не пересобирается, а перетегируется.

    Задача 17. Алерты в Prometheus

    Уровень: ★★☆ · Время: ~45 мин

    Цель. Добавить в стек из задачи 4 правила алертов и увидеть, как алерт проходит Pending → Firing.

    Требования.

    • InstanceDown: таргет недоступен дольше 1 минуты;
    • HighCPU: загрузка CPU узла выше 80 % дольше 2 минут;
    • у алертов severity и понятный summary с именем инстанса;
    • уронить node-exporter и пронаблюдать в /alerts.
    Решение 
    # alerts.yml
groups:
  - name: basic
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 1m
        labels: { severity: critical }
        annotations:
          summary: "{{ $labels.job }} ({{ $labels.instance }}) недоступен"
      - alert: HighCPU
        expr: 100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[2m])) * 100 > 80
        for: 2m
        labels: { severity: warning }
        annotations:
          summary: "CPU {{ $labels.instance }}: {{ $value | humanize }}%"

    В prometheus.yml: rule_files: [/etc/prometheus/alerts.yml] + смонтировать файл. Проверка синтаксиса: docker compose exec prometheus promtool check rules /etc/prometheus/alerts.yml. docker compose stop node-exporter → через ~15 с Pending, через 1 мин Firing. for защищает от ложных срабатываний на кратковременный сбой. Отправка уведомлений — Alertmanager.

    Задача 18. Скрипт проверки доступности сайтов

    Уровень: ★★☆ · Время: ~45 мин

    Цель. Скрипт для cron или CI: проверяет список URL и возвращает код выхода.

    Требования.

    • URL — из файла (по одному в строке, # — комментарий);
    • таймаут 5 с, до 3 попыток с паузой;
    • вывод: OK 200 0.123s https://... / FAIL 000 https://...;
    • код выхода 1, если хоть один URL недоступен;
    • set -euo pipefail, shellcheck без замечаний.
    Решение 
    #!/usr/bin/env bash
set -euo pipefail

file="${1:?usage: $0 urls.txt}"
failed=0

while IFS= read -r url || [ -n "$url" ]; do
  [[ -z "$url" || "$url" == \#* ]] && continue
  result=$(curl -s -o /dev/null --max-time 5 --retry 2 --retry-delay 2 --retry-all-errors \
           -w '%{http_code} %{time_total}' "$url" || true)
  code=${result%% *}
  if [[ "$code" =~ ^[23] ]]; then
    printf 'OK   %s  %ss  %s\n' "$code" "${result#* }" "$url"
  else
    printf 'FAIL %s  %s\n' "${code:-000}" "$url"
    failed=1
  fi
done < "$file"

exit "$failed"

    || [ -n "$url" ] — чтобы не потерять последнюю строку без перевода строки. || true после curl — иначе set -e оборвёт скрипт на первом недоступном URL. --retry-all-errors — повторять и при ошибках соединения, а не только при 5xx.

    Задача 19. Диск полон, а файлов нет

    Уровень: ★★★ · Время: ~30 мин

    Цель. Классика собеседований: df показывает занятое место, а du его не находит.

    docker run -it --rm ubuntu:24.04 bash
apt-get update -qq && apt-get install -y -qq lsof procps
dd if=/dev/zero of=/tmp/big.log bs=1M count=500
tail -f /tmp/big.log > /dev/null &
rm /tmp/big.log
df -h /tmp ; du -sh /tmp

    Требования. Объяснить, почему место не освободилось; найти процесс; освободить место без перезапуска процесса.

    Решение

    Файл удалён из каталога (удалена ссылка), но процесс tail держит его открытым — данные живут, пока открыт дескриптор. du считает файлы в дереве каталогов, df — занятые блоки файловой системы.

    lsof +L1                                   # открытые файлы с 0 ссылок: COMMAND, PID, FD
ls -l /proc/*/fd 2>/dev/null | grep deleted
: > /proc/<PID>/fd/<FD>                    # обнулить файл через дескриптор — место освобождается

    В проде так бывает с логами: logrotate удалил файл, а сервис продолжает писать в старый дескриптор. Правильно — copytruncate или сигнал сервису переоткрыть логи (nginx -s reopen, SIGHUP).

    Задача 20. Идемпотентный playbook

    Уровень: ★★☆ · Время: ~1 ч

    Цель. Playbook, который при повторном запуске ничего не меняет (changed=0).

    Требования (целевой хост — контейнер python:3.12-slim, в нём уже есть Python):

    • подключение к контейнеру без SSH — connection-плагин Docker;
    • установить пакет curl; создать пользователя deploy; каталог /opt/app владельца deploy;
    • из шаблона создать /opt/app/config.ini с переменной env;
    • строка MaxSessions 10 в /etc/app.conf — добавить, не дублируя;
    • второй запуск: changed=0.
    docker run -d --name target python:3.12-slim sleep infinity
ansible-galaxy collection install community.docker
    Решение 
    # inventory.ini
[lab]
target ansible_connection=community.docker.docker ansible_python_interpreter=/usr/local/bin/python3

    # site.yml
- hosts: lab
  become: false
  vars:
    env: dev
  tasks:
    - name: curl
      ansible.builtin.apt: { name: curl, state: present, update_cache: true, cache_valid_time: 3600 }
    - name: user deploy
      ansible.builtin.user: { name: deploy, system: true }
    - name: app dir
      ansible.builtin.file: { path: /opt/app, state: directory, owner: deploy, mode: "0755" }
    - name: config
      ansible.builtin.template: { src: config.ini.j2, dest: /opt/app/config.ini, owner: deploy, mode: "0640" }
    - name: max sessions
      ansible.builtin.lineinfile: { path: /etc/app.conf, line: "MaxSessions 10", create: true }

    config.ini.j2: [app] и env = {{ env }}. Запуск: ansible-playbook -i inventory.ini site.yml (дважды). cache_valid_time — иначе apt update_cache будет changed на каждом запуске. Модули command/shell не идемпотентны сами по себе — для них нужны creates: или changed_when:.

    SRE

    Задача 22. Runbook и postmortem

    Уровень: ★★☆ · Время: ~1 ч

    Цель. Написать два документа, которые пишут на работе после настоящих инцидентов.

    Требования.

    1. Runbook для алерта «HighErrorRate: доля 5xx API > 5 % за 5 минут»: что значит, как проверить, частые причины, шаги устранения, когда эскалировать.
    2. Blameless postmortem по инциденту из диплома: сборки падали из-за таймаутов gcr.io (журнал проблем, № 23): хронология, влияние, причина, что помогло, action items с владельцами.
    Решение

    Runbook (скелет).

    1. Что значит: пользователи получают ошибки на ≥5 % запросов API.
    2. Проверить: дашборд R.E.D. — ошибки на всех маршрутах или одном; когда начались; был ли деплой (helm history).
    3. Частые причины → действие: свежий деплой → helm rollback; поды не Ready / рестарты → kubectl describe, logs --previous; зависимость (БД, внешний API) недоступна → её статус; упор в ресурсы → HPA, лимиты.
    4. Эскалация: > 15 минут без улучшения или > 20 % ошибок — дежурный разработчик сервиса.

    Postmortem (скелет). Резюме (2–3 строки) → Влияние (сколько релизов задержано, на сколько) → Хронология с временем → Причина (сеть раннеров нестабильно достаёт gcr.io — внешняя зависимость в критическом пути сборки) → Что сработало / что нет (Retry помогал не всегда) → Action items: базовый образ scratch (сделано), база Trivy с ghcr.io (сделано), ревизия всех внешних зависимостей CI (владелец, срок). Без поиска виноватых: «что в системе позволило этому случиться».

    Задача 23. Argo CD для k8s-platform-lab

    Уровень: ★★★ · Время: ~1,5 ч

    Цель. Деплой из git: изменение в репозитории само попадает в кластер, ручные правки откатываются.

    Требования.

    • Argo CD в кластере platform-lab, доступ к UI через port-forward;
    • Application смотрит на чарт charts/my-app твоего репозитория на GitHub, ветка task/23-gitops;
    • релиз в отдельном namespace my-app-gitops, Ingress выключен (иначе конфликт с релизом make deploy за тот же путь /);
    • automated: { prune: true, selfHeal: true };
    • изменить config.LOG_LEVEL в ветке → кластер подтянул; поправить ConfigMap руками → Argo CD вернул.
    Подсказка

    Образ k8s-platform-lab:dev должен быть загружен в kind (make build) — Argo CD его не соберёт. Значения для чарта задаются в spec.source.helm.

    Решение 
    kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
kubectl -n argocd port-forward svc/argocd-server 8443:443

    apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: my-app, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://github.com/FunnyJesus/k8s-platform-lab.git
    targetRevision: task/23-gitops
    path: charts/my-app
    helm:
      valuesObject:
        image: { repository: k8s-platform-lab, tag: dev }
        ingress: { enabled: false }
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app-gitops
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [CreateNamespace=true]

    Проверка selfHeal: kubectl -n my-app-gitops patch configmap my-app-config -p '{"data":{"LOG_LEVEL":"DEBUG"}}' → через несколько секунд значение снова из git. Argo CD опрашивает git раз в ~3 минуты (быстрее — Refresh в UI или webhook). Если включил профиль restricted (задача 7) — повесь метки и на my-app-gitops. Подробнее — GitOps.
