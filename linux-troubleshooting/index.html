    Linux: диагностика и производительность

    «Сервер тормозит / сайт не отвечает — твои действия?» — самый частый практический вопрос на собеседовании. Ниже — порядок проверки и команды для каждого ресурса.

    Базовые команды — Linux: команды. Сетевая диагностика подробнее — Сети. Разбор реальных ситуаций — Типовые инциденты.

    Первые 60 секунд на сервере

    Прежде чем что-то чинить — быстро собрать картину. Последовательность (идея Брендана Грегга из Netflix):

    uptime                 # load average: растёт или падает?
dmesg -T | tail -20    # ошибки ядра: OOM killer, диск, сеть
free -h                # память и swap
df -h                  # место на дисках
df -i                  # inodes (место может «кончиться» при свободных гигабайтах)
top                    # кто ест CPU / память прямо сейчас (или htop)
vmstat 1 5             # CPU, память, I/O, очередь процессов по секундам
iostat -xz 1 3         # нагрузка на диски (пакет sysstat)
ss -tulpn              # какие порты слушаются и какими процессами
journalctl -p err -n 50 --no-pager   # последние ошибки в системном журнале

    Метод USE для каждого ресурса (CPU, память, диск, сеть) — проверить три вещи:

    Буква Что Пример для CPU
    Utilization Насколько ресурс занят %us + %sy в top
    Saturation Есть ли очередь ожидающих load average > числа ядер
    Errors Есть ли ошибки dmesg, счётчики ошибок

    CPU и load average

    nproc                  # сколько ядер
uptime                 # load average: 1.52, 0.98, 0.60  → за 1, 5, 15 минут
top                    # затем: P — сорт. по CPU, M — по памяти, 1 — по ядрам
ps aux --sort=-%cpu | head    # топ процессов по CPU

    Load average — среднее количество процессов, которые выполняются или ждут (CPU или диск). Сравнивать с числом ядер:

    Load на 4-ядерном сервере Значит
    1.0 загружено ~25%, всё спокойно
    4.0 все ядра заняты полностью
    12.0 очередь в 3 раза больше, чем ядер — всё тормозит

    Строка %Cpu(s) в top:

    Поле Что значит Если высокое
    us код приложений приложение много считает — профилировать
    sy ядро много системных вызовов, переключений
    wa ожидание I/O упираемся в диск, а не в CPU
    st steal — CPU забрал гипервизор «шумный сосед» на виртуалке, облачный лимит

    Высокий load при низком us и высоком wa — проблема в диске, а не в процессоре.

    Память

    free -h
#               total   used   free  shared  buff/cache  available
# Mem:           7.7Gi  3.1Gi  512Mi  120Mi    4.1Gi       4.2Gi
ps aux --sort=-%mem | head      # топ по памяти
    • Смотри на available, а не на free. Linux использует свободную память под кеш диска (buff/cache) и отдаёт её приложениям по требованию. Маленький free — это нормально.
    • Swap активно используется (vmstat колонки si/so не нули) — памяти реально не хватает, всё будет тормозить.

    OOM killer

    Когда память кончилась совсем, ядро убивает процесс с наибольшим «весом».

    dmesg -T | grep -i -E "killed process|out of memory"
journalctl -k | grep -i oom

    В Kubernetes то же самое выглядит как OOMKilled в kubectl describe pod — контейнер превысил resources.limits.memory.

    Диск

    df -h                          # заполненность файловых систем
df -i                          # заполненность inodes
du -sh /var/* | sort -rh | head      # что занимает место
du -xh / --max-depth=2 2>/dev/null | sort -rh | head -20
iostat -xz 1                   # %util ~100 и большой await → диск перегружен
iotop                          # какой процесс пишет/читает (нужен root)

    Частые причины «кончилось место»:

    • логи (/var/log, логи Docker в /var/lib/docker/containers);
    • старые образы и тома Docker → docker system df, docker system prune;
    • журнал systemd → journalctl --disk-usage, journalctl --vacuum-size=500M;
    • удалённый файл, который держит процесс — место не освобождается:
    lsof +L1                       # открытые, но удалённые файлы
# решение: перезапустить процесс (или обнулить через /proc/<pid>/fd/<n>)

    Процессы

    ps aux | grep nginx            # найти процесс
ps -ef --forest                # дерево процессов
pstree -p                      # то же, наглядно
pgrep -a python                # PID + команда по имени
kill <pid>                     # SIGTERM — вежливо попросить завершиться
kill -9 <pid>                  # SIGKILL — убить без вопросов (последнее средство)

    Состояния процессов (колонка STAT):

    Состояние Значение
    R выполняется
    S спит, ждёт события (нормально)
    D непрерываемый сон — обычно ждёт диск/NFS; не убивается даже kill -9
    Z зомби — завершился, но родитель не забрал код выхода

    Что процесс делает прямо сейчас

    lsof -p <pid>                  # какие файлы и сокеты открыты
lsof -i :8080                  # кто занял порт 8080
strace -p <pid> -f -e trace=network,file   # какие системные вызовы делает
strace -c -p <pid>             # статистика вызовов (Ctrl+C — вывести)
cat /proc/<pid>/status         # память, потоки, состояние
ls -l /proc/<pid>/cwd          # рабочая директория процесса
cat /proc/<pid>/environ | tr '\0' '\n'   # переменные окружения

    Сеть

    ss -tulpn                      # слушающие порты
ss -tanp | grep :5432          # соединения к порту
ss -s                          # сводка: сколько соединений в каком состоянии
curl -v http://localhost:8080/health   # ответ сервиса изнутри сервера
curl -w "%{time_total}\n" -o /dev/null -s https://example.com   # время ответа
dig example.com +short         # DNS
ping -c 3 10.0.0.5 && traceroute 10.0.0.5
tcpdump -i any port 80 -nn     # сырые пакеты

    Много соединений в TIME_WAIT / CLOSE_WAIT:

    • TIME_WAIT — нормальное состояние после закрытия, но тысячи штук = клиент открывает новое соединение на каждый запрос (нет keep-alive/пула).
    • CLOSE_WAIT — ошибка в приложении: удалённая сторона закрыла соединение, а приложение своё — нет. Растёт — утечка соединений.

    Логи и systemd

    systemctl status nginx                  # статус + последние строки лога
systemctl --failed                      # все упавшие юниты
journalctl -u nginx -f                  # лог сервиса в реальном времени
journalctl -u nginx --since "10 min ago"
journalctl -b -p warning                # предупреждения с момента загрузки
tail -f /var/log/syslog                 # классические логи (Debian/Ubuntu)

    Лимиты

    ulimit -n                               # лимит открытых файлов для текущего shell
cat /proc/<pid>/limits                  # лимиты конкретного процесса
cat /proc/sys/fs/file-nr                # открыто файлов в системе / максимум

    Ошибка Too many open files → поднять лимит (LimitNOFILE= в systemd-юните или /etc/security/limits.conf) и проверить, нет ли утечки файловых дескрипторов.

    Алгоритм «сервис не работает»

    1. Процесс жив? systemctl status app / ps aux | grep app
    2. Порт слушается? ss -tulpn | grep 8080
    3. Отвечает локально? curl -v localhost:8080
    4. Что в логах? journalctl -u app -n 100
    5. Ресурсы? df -h, free -h, uptime, dmesg -T | tail
    6. Снаружи доступен? firewall (iptables -L -n, ufw status), security group, DNS
    7. Зависимости? база, кеш, внешний API — nc -zv db-host 5432
    8. Что менялось? последний деплой, конфиг, обновление пакетов

    Частые ошибки

    Симптом Причина Решение
    No space left on device, а df -h показывает свободное место кончились inodes (миллионы мелких файлов) df -i, найти и удалить мелкие файлы (кеш, сессии)
    Удалили большой лог, место не освободилось файл держит открытым процесс lsof +L1, перезапустить процесс; в будущем — logrotate
    «Памяти свободно 200 МБ, всё плохо» смотрят на free, а не available ориентироваться на available и активность swap
    Load 20, CPU почти не занят процессы ждут диск (wa, состояние D) iostat -xz, iotop — искать, кто грузит диск
    Процесс не убивается kill -9 состояние D — ждёт I/O разбираться с диском/NFS; иногда помогает только перезагрузка

    Best Practices

    • Сначала собрать картину, потом чинить — первые 60 секунд экономят часы.
    • Сравнивай с нормой — без мониторинга непонятно, load 8 — это много или обычно.
    • Не перезагружай сразу — сначала сохрани логи и вывод команд, иначе причина исчезнет.
    • Настрой logrotate и лимиты заранее — большинство «кончилось место» предотвращаются.
    • Записывай шаги — они станут runbook-ом (см. SRE).
