    CD: стратегии деплоя (подробно)

    Способ, которым новая версия приложения раскатывается по репликам/окружению. Выбор стратегии влияет на доступность, откат и риск.

    Теория CD — Continuous Delivery (теория). Мини-шпаргалка — CD: шпаргалка топ-20.

    Основные параметры стратегии

    • Даунтайм — будет ли кратковременная остановка сервиса при деплое
    • Скорость — как быстро раскатывается новая версия
    • Риск — насколько опасно сломать прод при выкатке
    • Откат — насколько легко вернуть предыдущую версию
    • Стоимость ресурсов — нужно ли держать двойные пулы машин

    1. Recreate (удалить и создать)

    Старая версия полностью останавливается, затем стартует новая.

    strategy:
  type: Recreate   # Kubernetes

    Плюсы: просто, никаких конфликтов версий. Минусы: даунтайм (есть период, когда сервис недоступен). Для большинства прод-сервисов неприемлемо. Когда: небольшие внутренние сервисы, где неважна доступность.

    2. Rolling update (обновление по очереди)

    Реплики старой версии постепенно заменяются новыми по одной/партиями. В каждый момент часть реплик работает на старой, часть — на новой версии.

    strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0      # не допускать даунтайма
    maxSurge: 1            # можно поднять 1 лишнюю реплику сверху

    Плюсы: без даунтайма, дешёв в ресурсах (тот же пул машин). Минусы: в момент деплоя и старые, и новые версии обслуживают трафик — нужна обратная совместимость (совместимость АПИ/БД). Контроль доли медленнее. Когда: большинство сервисов по умолчанию (K8s дефолт).

    3. Blue-green (синий-зелёный)

    Держатся два идентичных окружения: blue (текущее) и green (новое). Новая версия разворачивается в green полностью, прогоняются тесты, и трафик мгновенно переключается на green (через балансировщик/роутер).

    Traffic → LB ──► blue (старая v1)   ← перед деплоем
                ──► green (новая v2) ← подготовлено, ждёт

После переключения:
Traffic → LB ──► blue (простаивает, резерв)
                ──► green (v2, обслуживает)

    Плюсы: быстрый откат — переключить трафик обратно на blue за секунды. Даунтайма нет, пользователи всегда на одной версии. Минусы: дорого — нужно держать двойной пул ресурсов (2 окружения одновременно). Нужен умный роутер/LB. Когда: когда критичен мгновенный откат и есть ресурсы.

    4. Canary (канареечный)

    Новая версия выкатывается на малую долю пользователей/трафика (например, 5%), постепенно увеличивая долю, пока не заменит всё.

    v1:  100% ──► v2: 5% / v1: 95% ──► v2: 50% / v1: 50% ──► v2: 100%

    Правка весов через балансировщик (nginx, Istio, K8s service).

    Плюсы: низкий риск — если новая версия ломается, страдает только малая часть; можно откатить до полного раската. Реальный фидбек на небольшой аудитории. Минусы: сложнее настройка, нужен мониторинг метрик для решения «раскатывать дальше или нет». Дольше полный деплой. Когда: крупные релизы, где важна уверенность, медицинские/финтех сервисы.

    5. A/B тестирование (разновидность canary)

    Две версии подаются заранее разным пользователям (по признаку: регион, тег, %). Отличие от canary — здесь часто осознанно хотят сравнить поведение, а не просто безопасно выкатить.

    Сравнительная таблица стратегий

    Стратегия Даунтайм Откат Риск Стоимость ресурсов Сложность
    Recreate ✅ есть медленный средний низкая низкая
    Rolling ❌ нет медленный средний (смешанные версии) низкая низкая
    Blue-green ❌ нет мгновенный низкий высокая средняя
    Canary ❌ нет быстрый низкий средняя высокая

    Как выбрать

    • Нужен мгновенный откат и есть ресурсы → blue-green
    • Хочешь проверить на малой доле с полным контролем → canary
    • Юнит/интеграция, не критична доступность → rolling (дефолт)
    • Внутренний сервис, неважен даунтайм → recreate

    Реализация в инструментах

    • Docker Compose — docker compose up --scale + ручное управление, обычно rolling.
    • Kubernetes — strategy.type: RollingUpdate (дефолт), Recreate, canary через несколько Deployments + Ingress/Service weights.
    • GitLab/GitHub CD — через when: manual + stages, прод-джобы часто blue-green/canary.
    • Арgo CD / Flux (GitOps) — желаемое состояние в git, автоматический sync.
