# Очереди сообщений: Kafka и RabbitMQ

> Мониторинг экспортёров — [Мониторинг](monitoring.md). Запуск в Kubernetes — [K8s](k8s.md) (StatefulSet).

**Брокер сообщений** — посредник между сервисами: один сервис **публикует** сообщение, другой **забирает и обрабатывает**, когда может. Сервисы не ждут друг друга и не знают друг о друге напрямую.

## Зачем

```
Без брокера:   API ──HTTP──► сервис писем     (сервис писем упал → заказ не оформлен)

С брокером:    API ──► [очередь "orders"] ──► сервис писем
                                          ├─► сервис аналитики
                                          └─► сервис склада
```

| Задача | Как помогает брокер |
|---|---|
| **Асинхронность** | API быстро отвечает пользователю, тяжёлая работа — потом (письма, генерация отчётов) |
| **Сглаживание пиков** | 10 000 заказов за минуту копятся в очереди, обработчики разбирают в своём темпе |
| **Развязка сервисов** | получатель упал — сообщения подождут, отправитель не пострадает |
| **Один отправитель — много получателей** | событие «заказ создан» получают склад, аналитика, уведомления |

## Kafka vs RabbitMQ

| | RabbitMQ | Kafka |
|---|---|---|
| Модель | **очередь**: сообщение забрали и подтвердили → удалено | **журнал (лог)**: сообщения хранятся заданное время, их можно перечитывать |
| Маршрутизация | гибкая: exchanges, routing keys | простая: топик + партиция |
| Пропускная способность | десятки тысяч сообщений/с | сотни тысяч – миллионы/с |
| Порядок | в пределах очереди | в пределах партиции |
| Повторное чтение | нет | да — сдвинуть offset назад |
| Типичные задачи | фоновые задачи, RPC, маршрутизация команд | потоки событий, логи, CDC, стриминг аналитики |

Коротко: **RabbitMQ — «почтальон»** (доставить задачу исполнителю), **Kafka — «журнал событий»** (записать всё, что произошло, чтобы разные системы читали в своём темпе).

Ещё встречаются: **NATS** (лёгкий и быстрый), **Redis Streams**, облачные **SQS/SNS** (AWS), **Google Pub/Sub**.

## RabbitMQ

### Понятия

```
producer ──► exchange ──(routing key / binding)──► queue ──► consumer
```

| Понятие | Что это |
|---|---|
| **Producer** | отправитель |
| **Exchange** | «сортировочный узел»: решает, в какие очереди положить сообщение |
| **Queue** | очередь, где сообщения ждут обработки |
| **Binding** | правило связи exchange → queue |
| **Consumer** | получатель |
| **Ack** | подтверждение обработки; без ack сообщение вернётся в очередь |
| **DLX / DLQ** | dead letter exchange/queue — куда попадают сообщения, которые не удалось обработать |

Типы exchange: `direct` (по точному ключу), `topic` (по шаблону `order.*`), `fanout` (всем очередям), `headers`.

### Запуск и управление

```bash
docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:4-management
# UI: http://localhost:15672  (guest / guest — только с localhost)

rabbitmqctl list_queues name messages consumers     # очереди, сколько сообщений, сколько получателей
rabbitmqctl list_connections
rabbitmqctl add_user app 'secret'
rabbitmqctl set_permissions -p / app ".*" ".*" ".*"
rabbitmq-diagnostics status
rabbitmq-diagnostics check_port_connectivity
```

### Что мониторить

* **messages ready** — растёт длина очереди → получатели не успевают;
* **unacked** — много неподтверждённых → получатели зависают на обработке;
* **consumers = 0** — очередь никто не читает;
* память и диск: при нехватке RabbitMQ включает **alarm** и перестаёт принимать сообщения.

## Kafka

### Понятия

```
producer ──► topic "orders"
               ├── partition 0: [m0][m1][m2][m3] ...  ◄── consumer A (group "billing")
               ├── partition 1: [m0][m1][m2] ...      ◄── consumer B (group "billing")
               └── partition 2: [m0][m1] ...          ◄── consumer C (group "billing")
                                                      ◄── group "analytics" читает всё независимо
```

| Понятие | Что это |
|---|---|
| **Broker** | сервер Kafka; кластер — несколько брокеров |
| **Topic** | именованный поток сообщений |
| **Partition** | часть топика; единица параллелизма и порядка |
| **Offset** | номер сообщения в партиции |
| **Consumer group** | группа получателей, делящих партиции между собой. Разные группы читают топик независимо |
| **Replication factor** | на скольких брокерах копия каждой партиции |
| **Retention** | сколько хранить сообщения (время или размер) |
| **KRaft** | встроенный консенсус; раньше для метаданных нужен был ZooKeeper (в Kafka 4.x ZooKeeper удалён) |

Важные следствия:

* **Параллелизм группы ≤ числа партиций.** 3 партиции + 5 получателей в группе → 2 будут простаивать.
* **Порядок гарантирован только внутри партиции.** Сообщения с одним ключом (например, `user_id`) всегда попадают в одну партицию.

### Команды

```bash
# топики
kafka-topics.sh --bootstrap-server localhost:9092 --list
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# отправить / прочитать (для отладки)
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning

# consumer groups и отставание (lag)
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing
# колонки: CURRENT-OFFSET  LOG-END-OFFSET  LAG

# перечитать с начала (группа должна быть остановлена)
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group billing \
  --reset-offsets --to-earliest --topic orders --execute
```

Удобные инструменты: **kcat** (`kcat -b localhost:9092 -L`), UI — **Kafka UI (Provectus)**, **AKHQ**, **Redpanda Console**. В Kubernetes Kafka обычно ставят оператором **Strimzi**.

### Что мониторить

* **Consumer lag** — главная метрика: насколько получатели отстают. Растёт → не успевают (добавить получателей/партиции, ускорить обработку).
* **Under-replicated partitions** > 0 — какой-то брокер отстаёт или лежит, риск потери данных.
* **Offline partitions** > 0 — партиция недоступна, запись/чтение в неё невозможны.
* Диск брокеров — retention и объём данных.

Экспортеры: `kafka-exporter` (lag), JMX exporter (метрики брокера).

## Гарантии доставки

| Гарантия | Значит | Цена |
|---|---|---|
| **At most once** | может потеряться, но без дублей | быстро, но теряем данные |
| **At least once** | не потеряется, но **могут быть дубли** | стандарт на практике |
| **Exactly once** | ровно один раз | сложно, дорого, ограниченно |

Отсюда правило: **обработчик должен быть идемпотентным** — повторная обработка того же сообщения не должна ломать данные (например, проверка `order_id` перед списанием денег).

## Частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Очередь/lag растёт бесконечно | получатели не успевают или упали | масштабировать consumers (Kafka — до числа партиций), искать медленную обработку |
| Сообщение крутится по кругу и валит получателя | «ядовитое» сообщение, бесконечный retry | лимит попыток + DLQ |
| Двойное списание / дубли | at-least-once без идемпотентности | идемпотентный обработчик, ключ дедупликации |
| Добавили consumers в Kafka — быстрее не стало | партиций меньше, чем получателей | увеличить число партиций (заранее с запасом) |
| RabbitMQ перестал принимать сообщения | memory/disk alarm | освободить ресурсы, разобрать очереди, лимиты длины |
| Потеря сообщений при падении брокера Kafka | `replication-factor=1` или `acks=0/1` | RF=3, `min.insync.replicas=2`, `acks=all` |

## Best Practices

* **Мониторинг длины очереди / consumer lag** с алертами — первое, что настраивать.
* **DLQ и лимит повторов** для необработанных сообщений.
* **Идемпотентные обработчики** — дубли будут.
* **Kafka: RF=3**, партиций с запасом, ключ сообщения — по сущности, где нужен порядок.
* **Брокеры — stateful**: для прода — managed-сервис или оператор (Strimzi, RabbitMQ Cluster Operator), а не голый Deployment.
