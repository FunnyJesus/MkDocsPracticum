# Git

Git — распределённая система контроля версий. Позволяет хранить историю изменений файлов, работать над проектом нескольким людям одновременно и откатываться к любой версии.

`HEAD` - указатель на текущую ветку или прямо на коммит. Именно к нему привязывается следующий создаваемый коммит.

>commit 8d50bdc760d773c22113fc7d3e353ecf099c7e13 (HEAD -> main, origin/main, origin/HEAD)
>
>Author: Райн Гослинг <118374481+Driver@users.noreply.github.com>
>Date:   Sun May 10 14:31:19 2026 +0300
>
>    Initial commit

`hash` - уникальный код коммита. Для удобства можно использовать первые 7 символов хеша вместо всех 40.

> Команды Git — на странице [Git: команды с подробным описанием](git-commands.md).
> Мини-шпаргалка: [Git: шпаргалка топ-20 команд](git-cheatsheet.md).

## Модель Git: три области

Git работает с тремя «областями», и любое изменение проходит через них по цепочке:

```
Рабочий каталог  →  Индекс (staging)  →  Репозиторий (коммит)
   (файлы)            (git add)              (git commit)
```

1. **Рабочий каталог (working directory)** — файлы, которые вы редактируете. Изменения здесь ещё «не в Git».
2. **Индекс / staging area** — «черновик» изменений, которые вы собрались коммитить. Что выбрали `git add` — то и попадёт в коммит.
3. **Репозиторий (HEAD)** — зафиксированные коммиты. Только они — история.

> Ключевая идея: `git add` и `git commit` — это РАЗНЫЕ действия. `add` кладёт в индекс, `commit` фиксирует индекс как коммит. Можно добавить в индекс не всё, а только нужные файлы.

### Статусы файлов

| Статус | Что значит |
|---|---|
| `untracked` | файл новый, Git ещё не следит за ним (не было `git add`) |
| `modified` | файл отслеживается, но изменился после последнего коммита |
| `staged` | изменение добавлено в индекс (`git add`), готово к коммиту |
| `committed` | изменение зафиксировано коммитом |

```bash
$ git status
On branch main
Changes to be committed:        # staged
        modified:   docs/git.md
```

## Коммит — снапшот состояния

**Коммит** — это снимок (snapshot) всего проекта в конкретный момент + метаданные:
- `hash` — уникальный идентификатор коммита
- `parent` — хеш предыдущего коммита (так строится цепочка-история)
- автор и дата
- сообщение (`commit message`) — что сделано

В отличие от систем вида «патчи/дельты», Git хранит полное состояние. Цепочка выглядит так:

```
A ← B ← C ← D (main, HEAD)
```

> Каждый коммит ссылается на предыдущего родителя — поэтому история линейна и её легко просматривать (`git log`) и откатываться.

## Ветки — это просто указатели

**Ветка** — это именованный указатель на коммит. Создать ветку = «поставить стрелку» на текущий коммит и двигаться от неё отдельно.

```
main:      A ← B ← C
                 \
feature:          D ← E
```

- `git branch <имя>` — создать ветку (указатель на текущий HEAD)
- `git checkout <имя>` / `git switch <имя>` — переключиться на ветку
- `git checkout -b <имя>` — создать и сразу переключиться

> Секрет веток: это НЕ «копии кода», а дешёвые указатели на коммиты. Поэтому ветки создаются мгновенно и стоят почти ничего.

`HEAD` показывает, на какой ветке/коммите вы сейчас. При переключении ветки `HEAD` движется на её вершину, а рабочий каталог перестраивается под неё.

## Слияние веток: merge vs rebase

### merge — слияние с созданием merge-коммита

`git merge <ветка>` вливает изменения одной ветки в текущую. История сохраняет обе линии и фиксирует точку слияния отдельным merge-коммитом.

```
было:   main: A---B
              \
feature:       C---D
после:  main: A---B---E   (E — merge commit, объединяет B и D)
              \       /
feature:       C---D
```

### fast-forward

Если в `main` после расхождения ничего не менялось, Git может просто передвинуть указатель — это **fast-forward** (без merge-коммита):

```
было:   main: A---B
              \
feature:       C---D
после:  main: A---B---C---D   (просто сдвинули указатель main)
```

### rebase — перенос ветки на новый базис

`git rebase <ветка>` переписывает историю: «пересаживает» коммиты ветки на вершину другой, выстраивая линейную историю.

```
было:   main: A---B
              \
feature:       C---D
после:  main: A---B---C'---D'   (C' и D' — те же коммиты, но на базе B)
```

> Итог тот же — код объединён, но история линейная и чистая. Минус: `rebase` **переписывает** коммиты (меняет их хеши). Правило: не делай rebase с ветками, которые уже в удалённом репозитории у других людей — сломаешь им историю.

### merge vs rebase — когда что

| Критерий | merge | rebase |
|---|---|---|
| История | с merge-коммитом, ветвится | линейная, чистая |
| Переписывает коммиты | нет | да (меняет хеши) |
| Безопасно для общих веток | да | нет |
| Когда использовать | по умолчанию, для общих веток | для личных веток / перед PR |

## Удалённый репозиторий и remote

Локальный репозиторий — это копия на вашей машине. Чтобы работать вместе, нужен **удалённый репозиторий** (удалённый сервер: GitHub, GitLab). Связь с ним описывает `remote`.

`origin` — стандартное имя удалённого репозитория, из которого склонировали проект.

```
Локальная ветка main  ↔  origin/main (удалённая)
       ↕ push / pull / fetch
        GitHub / GitLab
```

### Основные операции с удалённым репозиторием

| Команда | Что делает |
|---|---|
| `git clone <url>` | скопировать удалённый репозиторий к себе (полная копия) |
| `git push` | отправить локальные коммиты на удалённый репозиторий |
| `git fetch` | скачать изменения с удалённого, но НЕ сливать с локальной веткой |
| `git pull` | = `git fetch` + `git merge`, сразу обновить локальную ветку |

> `git pull` — это две команды под капотом: сначала `fetch` (скачал), потом `merge` (слил с местными). `fetch` только скачивает — полезно посмотреть изменения перед вливанием.

### clone vs fork

- **clone** — локальная копия репозитория (у вас в git появляется `origin`).
- **fork** — копия репозитория в вашем аккаунте на GitHub/GitLab (свой независимый origin), потом её клонируют. Классика для open source: fork → клон → ветка → PR.

## Откаты: reset / revert / checkout

Откаты бывают трёх видов — зависит от того, что откатываем.

| Команда | Что делает | Когда |
|---|---|---|
| `git reset` | двигает HEAD/индекс/рабочий каталог к указанному коммиту | локально, до push |
| `git revert <hash>` | создаёт НОВЫЙ коммит, который отменяет изменения указанного | безопасно, можно пушнуть |
| `git checkout <file>` / `git restore <file>` | откатывает файл в рабочем каталоге к последнему коммиту | выкинуть незакоммиченные правки |

```bash
git reset --hard HEAD        # вернуться к последнему коммиту, выкинуть правки
git revert abc1234           # новый коммит, отменяющий abc1234
git restore file.txt         # откатить конкретный файл
```

> `git reset` — только для локальной истории (до `push`). После `push` историю «переписывать» нельзя — используй `git revert`. Хорошая практика: лучше создать новый коммит (`revert`), чем переписывать историю (`reset`).

## Обязательные атрибуты

### Игнорирование файлов или каталогов

* `.gitignore` - файл, в котором содержаться имена файлов или целых каталогов, которые будет игнорировать при сохранении изменений

!!! Пример содержимого
    ```
    .terraform // файл
    terraform.tfstate
    terraform.tfstate.backup
    /test // каталог
    ```

> Секреты, временные файлы, зависимости и собранные артефакты не должны попадать в Git — для этого и нужен `.gitignore`.

## Разрешение конфликтов

Конфликты появляются, когда сливают две ветки кода, но изменения в них противоречат друг другу. `Git` автоматически не решает конфликты, поэтому их нужно решать самому.

#### Алгоритм

Пример: в основной ветке main разработчик изменил логику расчёта итоговой цены в корзине интернет-магазина, заменив фиксированную скидку discount на новую функцию calculate_seasonal_discount(). Тем временем в ветке feature/free-shipping в той же строке добавили учёт бесплатной доставки вызовом apply_free_shipping().

Алгоритм разрешения:
1. Открыть конфликтный файл `cart.py`.
2. Найти маркеры `<<<<<<<, =======, >>>>>>>`.
```
    # ... previous code ...
<<<<<<< HEAD
    total = apply_discount(total, calculate_seasonal_discount())
=======
    total = apply_free_shipping(total)
>>>>>>> feature/free-shipping
    return total
```
3. Выбрать нужный вариант или написать новый.
4. Удалить маркеры конфликта.
```
    # ... previous code ...
    total = apply_discount(total, calculate_seasonal_discount())
    total = apply_free_shipping(total)
    return total
```
5. Сохранить файл. <br>
6. Выполнить `git add cart.py` и `git commit`.
