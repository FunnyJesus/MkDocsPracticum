# Бэкапы и Disaster Recovery

> Бэкапы PostgreSQL подробно — [Базы данных](databases.md). Реакция на аварии — [SRE](sre.md).

Бэкап нужен не «на всякий случай», а под конкретные сценарии: удалили данные по ошибке, зашифровал вирус-шифровальщик, сгорел дата-центр, провайдер заблокировал аккаунт. **Disaster Recovery (DR)** — план, как восстановить работу после такой аварии и за какое время.

## RPO и RTO

```
         последний бэкап            авария                   сервис снова работает
─────────────●──────────────────────────✖───────────────────────────●──────────► время
             └──────── RPO ─────────────┘└─────────── RTO ──────────┘
               сколько данных потеряем      сколько будем лежать
```

| Метрика | Вопрос | Пример | Влияет на |
|---|---|---|---|
| **RPO** (Recovery Point Objective) | Сколько данных допустимо **потерять**? | 15 минут | как часто бэкапить (или реплицировать) |
| **RTO** (Recovery Time Objective) | Как долго допустимо **не работать**? | 1 час | как устроено восстановление |

RPO = 0 и RTO = 0 — очень дорого (синхронная репликация в несколько регионов). Цели выбираются с бизнесом: сколько стоит час простоя и час потерянных заказов.

## Правило 3-2-1

* **3** копии данных (оригинал + 2 бэкапа);
* на **2** разных типах носителей / в 2 разных системах;
* **1** копия — **вне основной площадки** (другой регион, другое облако, другой аккаунт).

Современное дополнение — **3-2-1-1-0**:

* **1** копия **неизменяемая (immutable)** или offline — её не удалит ни шифровальщик, ни злоумышленник с админскими правами (S3 Object Lock, WORM);
* **0** ошибок при проверке восстановления.

## Типы бэкапов

| Тип | Что копирует | Плюс | Минус |
|---|---|---|---|
| **Полный** | всё | простое восстановление | долго, много места |
| **Инкрементальный** | изменения с **последнего любого** бэкапа | быстро, мало места | для восстановления нужна вся цепочка |
| **Дифференциальный** | изменения с **последнего полного** | восстановление: полный + последний дифф | растёт со временем |
| **Снапшот** диска/тома | состояние диска на момент | мгновенно | обычно в том же облаке/регионе |
| **Непрерывный (WAL/binlog)** | поток изменений | восстановление на любой момент (PITR) | сложнее настроить |

> **Репликация — не бэкап.** Если выполнили `DROP TABLE`, реплика честно выполнит его тоже. Бэкап защищает от ошибок, репликация — от падения сервера.

## Что бэкапить

| Что | Как | Комментарий |
|---|---|---|
| Базы данных | pg_dump / pgBackRest / WAL-G, managed-бэкапы | самое ценное |
| Файлы пользователей (object storage) | версионирование бакета + репликация в другой регион | удаление ≠ потеря, если включено versioning |
| Тома Kubernetes (PV) | Velero + снапшоты CSI | stateful-приложения |
| Манифесты Kubernetes | **git** (GitOps) + Velero | при GitOps кластер восстанавливается из git |
| Terraform state | версионирование бакета | без state Terraform «забудет» инфраструктуру |
| Секреты и ключи | бэкап Vault, ключи sealed-secrets/SOPS/age | потеря ключа = потеря всех зашифрованных данных |
| Конфиги серверов | git + Ansible | сервер — «скот», а не «питомец»: пересоздаётся кодом |
| Registry | важные релизные образы | можно пересобрать, но долго |

## Инструменты

| Инструмент | Для чего |
|---|---|
| **restic** | бэкап файлов в S3/SFTP/локально: дедупликация, шифрование |
| **BorgBackup** | то же, классика для серверов |
| **rclone** | синхронизация с облачными хранилищами |
| **Velero** | бэкап ресурсов и томов Kubernetes |
| **pgBackRest / WAL-G / Barman** | PostgreSQL с PITR |
| Облачные | AWS Backup, снапшоты дисков, Yandex Cloud Backup |

### restic

```bash
export RESTIC_REPOSITORY=s3:s3.amazonaws.com/company-backups/web1
export RESTIC_PASSWORD_FILE=/etc/restic/password
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=...

restic init                                   # один раз
restic backup /srv/app /etc --exclude="*.log"
restic snapshots                              # список бэкапов
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune   # ротация
restic check                                  # проверить целостность репозитория
restic restore latest --target /tmp/restore   # восстановление
```

### Velero (Kubernetes)

```bash
velero install --provider aws --bucket k8s-backups --backup-location-config region=eu-central-1 ...

velero backup create shop-$(date +%F) --include-namespaces shop
velero schedule create daily --schedule="0 2 * * *" --ttl 720h     # каждый день, хранить 30 дней
velero backup get
velero restore create --from-backup shop-2026-09-26
velero restore create --from-backup shop-2026-09-26 --namespace-mappings shop:shop-restore-test
```

## Проверка восстановления

> **Бэкап, который ни разу не восстанавливали, — это надежда, а не бэкап.**

* **Автоматическое тестовое восстановление**: по расписанию поднять базу из бэкапа в отдельном окружении и выполнить проверочный запрос (`SELECT count(*) FROM orders`, дата последней записи).
* **Мониторинг бэкапов**: алерт, если последний успешный бэкап старше N часов, если размер резко изменился.
* **Замер RTO**: сколько реально заняло восстановление — укладываемся ли в цель.

```bash
# пример проверки в cron/CI
pg_restore -d restore_test latest.dump \
  && psql -d restore_test -tAc "select max(created_at) > now() - interval '1 day' from orders" | grep -q t \
  && echo "restore OK" || echo "restore FAILED"   # + отправить метрику/алерт
```

## Стратегии DR

| Стратегия | Как устроено | RTO | Цена |
|---|---|---|---|
| **Backup & Restore** | только бэкапы; при аварии поднимаем всё с нуля (IaC + данные) | часы – сутки | $ |
| **Pilot Light** | в резервном регионе минимум: реплика базы, инфраструктура описана кодом, серверов почти нет | десятки минут – часы | $$ |
| **Warm Standby** | уменьшенная копия прода работает в резервном регионе | минуты | $$$ |
| **Active-Active (multi-site)** | трафик идёт в оба региона одновременно | ~0 | $$$$ |

**Infrastructure as Code** — основа любой стратегии: если вся инфраструктура в Terraform/Ansible/GitOps, «поднять всё с нуля» — это часы, а не недели.

## DR-учения

План, который не отрабатывали, в реальной аварии не сработает: пароли устарели, скрипт не запускается, никто не помнит порядок.

* **Tabletop** — прогон сценария «на бумаге»: «регион недоступен — что делаем по шагам?»
* **Game day** — реальное восстановление в тестовом окружении по runbook.
* **Chaos engineering** — контролируемые поломки в проде (Chaos Mesh, LitmusChaos, AWS FIS), когда система уже зрелая.

## Частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Бэкап есть, восстановить не получается | ни разу не проверяли; нет ключа шифрования | регулярное тестовое восстановление, бэкап ключей отдельно |
| Шифровальщик удалил и бэкапы | бэкапы доступны с тех же учётных данных | immutable-копия (Object Lock), отдельный аккаунт |
| Бэкап в том же регионе/аккаунте, что и прод | «так проще» | копия в другом регионе/аккаунте (правило 3-2-1) |
| Бэкапы «тихо» перестали делаться месяц назад | нет мониторинга | алерт на возраст последнего успешного бэкапа |
| Думали, что реплика — это бэкап | репликация повторяет и ошибки | отдельные бэкапы с историей / PITR |
| Восстановились за 12 часов при RTO 1 час | RTO не измеряли | учения, замер реального времени |

## Best Practices

* **Сначала RPO/RTO с бизнесом**, потом выбор инструментов.
* **3-2-1-1-0**: копия вне площадки, immutable-копия, проверка восстановления.
* **Автоматическое тестовое восстановление** и алерты на бэкапы.
* **Вся инфраструктура — кодом**, тогда восстанавливать нужно только данные.
* **Runbook восстановления и регулярные учения.**
* **Бэкапь ключи шифрования и секреты** отдельно от данных.
