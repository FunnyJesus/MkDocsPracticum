# Памятка: от нуля до работающего сервиса

Что делать, когда дали приложение и задачу «подними инфраструктуру, собери, задеплой, настрой
мониторинг» — и непонятно, с чего начать. Порядок и чек-листы собраны по опыту
[дипломного проекта](diploma-momo-store.md); подробности и реальные грабли — в его разделах.

!!! tip "Главное правило"
    **Иди снизу вверх и проверяй каждый слой отдельно, прежде чем строить на нём следующий.**
    Если сломается пайплайн, в котором одновременно новые Dockerfile, реестр, кластер и чарт, —
    причину придётся искать во всех четырёх местах сразу. Если каждый слой уже проверен руками —
    сломаться может только последний.

## Кто что делает: ты, CI, кластер

Частая путаница: «CI делает все файлы, а потом раскатывает». Нет — **CI не создаёт файлы, он их
выполняет**. Файлы поставки пишешь ты, один раз, и коммитишь в репозиторий; CI на каждую версию
собирает по ним **артефакты** и раскатывает их.

```
 ТЫ (один раз, руками)        CI (на каждый коммит/тег)        КЛАСТЕР
 ─────────────────────        ─────────────────────────        ───────
 Dockerfile           ──►     docker build → образ :sha  ──►
 Helm-чарт            ──►     helm package → чарт 1.2.3  ──►   helm upgrade → поды
 .gitlab-ci.yml       ──►     (описывает шаги CI)
 Terraform            ──►     (запускается отдельно — кластер уже должен существовать)
```

| Что | Кто делает | Как часто | Где живёт |
|---|---|---|---|
| код поставки: Dockerfile, чарт, CI, Terraform | ты | один раз, потом правки | репозиторий |
| артефакты: образы, пакет чарта | CI | на каждую версию | реестр |
| развёрнутое приложение | CD-шаг CI (`helm upgrade`) или Argo CD | на каждый релиз | кластер |

«Зарелизить» = **поставить тег**: дальше всё делает пайплайн, написанный один раз.

**Сначала руками, потом в CI.** Пайплайн должен повторять команды, которые ты уже запускал руками и
которые сработали (`docker build`, `helm upgrade --install`). Если писать CI сразу, ошибку придётся
искать одновременно в Dockerfile, чарте, правах и пайплайне — по 5 минут на попытку.

**Если кластер даёт команда платформы** — Terraform не твоя задача: нужны namespace, kubeconfig с
правами только в нём и доступ к реестру. Начинай со слоя 7.

**Push или pull:** в push-модели CI сам делает `helm upgrade` (нужен kubeconfig в CI); в GitOps
CI только собирает образ и меняет версию в git, а Argo CD в кластере подтягивает изменения сам
(доступ CI в кластер не нужен) — см. [GitOps](gitops.md).

## Карта слоёв

```
 0. Разведка          что за приложение, что нельзя менять, бюджет, критерии готовности
 1. Приложение        запускается локально, отвечает на /health
 2. Образ             Dockerfile → образ запускается и отвечает
 3. Доступы           облако (биллинг, квоты, CLI), GitLab/GitHub (CI включён, раннер есть)
 4. IaC: bootstrap    бакет для state + сервисный аккаунт Terraform
 5. Инфраструктура    сеть, кластер, реестр, бакеты — terraform apply, plan = No changes
 6. Платформа         ingress, мониторинг, доступ CI в кластер
 7. Чарт              helm lint/template → ручной helm install → приложение отвечает
 8. CI                build → test (образы в реестре)
 9. CD                release → deploy по тегу, автооткат
10. Наблюдаемость     метрики, дашборд R.E.D., алерты
11. Сдача             README, чек-лист готовности, уборка
```

Каждый слой ниже — с вопросом «как проверить, что готово». Не переходи дальше, пока проверка не прошла.

## 0. Разведка (1–2 часа, без единой строки кода)

Цель — узнать ограничения **до** того, как они найдут тебя сами.

| Вопрос | Где узнать | Почему важно |
|---|---|---|
| Что за компоненты, на чём написаны | репозиторий, README, `go.mod`/`package.json` | от этого Dockerfile и сборка |
| Какие порты, эндпоинты `/health`, `/metrics` | код (роутер), README | пробы, Service, мониторинг |
| Какие переменные окружения и конфиги читает | `os.Getenv`, `process.env`, конфиг-файлы | ConfigMap/Secret в чарте |
| Внешние зависимости: БД, очереди, статика, CDN | код, конфиги | что ещё поднимать, куда ходит сеть |
| **Что менять нельзя** (исходники, версии, облако) | задание, тимлид | в дипломе правки кода пришлось откатывать |
| Бюджет и лимиты | задание, биллинг | прерываемые узлы, размер кластера, когда гасить |
| Где CI и есть ли раннеры | GitLab/GitHub проекта | без раннера пайплайн висит в `pending` |
| Критерии готовности | чек-лист задания | работаешь на них, а не «чтобы было» |
| Сетевые ограничения (РФ, корпоративная сеть) | проверить `curl` с раннера/из облака | Telegram, gcr.io, registry.terraform.io могут быть недоступны |

**Результат:** короткий план на 1 страницу: компоненты, схема, что где будет запущено, список рисков.

!!! warning "Чужой готовый репозиторий — ориентир, а не шаблон"
    Решение «как у прошлого выпуска» может быть устаревшим (версии, практики) и с ошибками
    безопасности (ключи в коде, пароли в README). Сверяй с текущим заданием.

## 1. Приложение запускается локально

```bash
# backend (Go)
go run ./cmd/api && curl -s localhost:8081/health
# frontend (Node)
npm ci && npm run build          # собирается ли вообще
```

**Готово, когда:** каждый компонент отвечает на свой health-эндпоинт; понятно, как frontend находит API
(переменная сборки? относительный путь?).

## 2. Образы

Чек-лист Dockerfile:

- [ ] multi-stage: сборка отдельно, в итоговом образе только результат;
- [ ] зависимости копируются **до** кода (кэш слоёв);
- [ ] минимальная база: `scratch`/`distroless` для статического бинарника, `-slim`/`-alpine` для остальных;
- [ ] **не root** (`USER` числом, если в образе нет `/etc/passwd`);
- [ ] `.dockerignore` (`.git`, `node_modules`, секреты);
- [ ] `hadolint Dockerfile` чистый; `trivy image` — нет исправимых CRITICAL;
- [ ] базовый образ **не тянется с нестабильного реестра** (у нас `gcr.io` таймаутил с раннеров).

```bash
docker build -t app:test .
docker run --rm -d -p 8080:8080 --read-only --name t app:test && curl -s localhost:8080/health
docker images app:test                  # размер
```

**Готово, когда:** образ собирается, запускается с `--read-only`, отвечает. Подробно —
[Диплом: образы](diploma-k8s.md).

## 3. Доступы и окружение

Самая недооценённая часть: в дипломе тут ушло больше времени, чем на код.

**Инструменты** (зафиксируй версии в README): `terraform`, `yc`/`aws`/..., `kubectl`, `helm`, `docker`.
Terraform ставится из `hashicorp/tap`, провайдеры в РФ — через зеркало
([как](diploma-terraform.md)).

**Облако:**

- [ ] платёжный аккаунт **ACTIVE** и привязан к облаку (иначе Object Storage — `AccessDenied` даже владельцу);
- [ ] квоты на зону: vCPU, RAM, **HDD/SSD** — посчитать под план и поднять **заранее**;
- [ ] CLI настроен (`yc init`), видны облако и каталог;
- [ ] бюджет с уведомлениями (50 % / 80 %).

```bash
yc quota-manager quota-limit list --service compute \
  --resource-type resource-manager.cloud --resource-id <cloud_id> | grep <zone>
yc storage bucket create --name test-<random>        # проверка биллинга; потом удалить
```

**Git-платформа:**

- [ ] CI/CD включён в проекте (у форков часто выключен: Settings → General → Visibility);
- [ ] есть раннер в статусе online, известны его теги;
- [ ] защищены ветка `main/master` и теги `v*`;
- [ ] **сеть раннера**: доступны ли реестры образов и внешние API, которые нужны пайплайну.

**Готово, когда:** тестовый бакет создаётся, квот хватает под план, пустой пайплайн из одной задачи
`echo ok` проходит на раннере.

## 4. Terraform: bootstrap

Проблема «курицы и яйца»: state хранится в бакете, а бакет создаёт Terraform.

1. `bootstrap/` с **локальным** state: сервисный аккаунт Terraform (+ роль), его ключ, статический
   ключ для S3, бакет для state с **версионированием**.
2. Ключи — **вне репозитория** (`~/.config/...`, права 600).
3. State bootstrap переносится в созданный бакет: `terraform init -migrate-state`.
4. Локальные копии state удаляются (в них ключи открытым текстом).

**Готово, когда:** `terraform plan` в bootstrap → `No changes`, а state лежит в бакете.
Пошагово — [Диплом: Terraform](diploma-terraform.md).

## 5. Инфраструктура

Порядок модулей: **сеть → реестр и бакеты → кластер → узлы**.

- [ ] `.gitignore`: `*.tfstate*`, `*.tfvars` (кроме `*.example`), `.terraform/`, ключи;
- [ ] `backend "s3"` с partial config (имя бакета в `backend.hcl`, ключи из env);
- [ ] IAM: `*_iam_member`, а не `*_iam_binding` (последний авторитативен — сотрёт чужие роли);
- [ ] минимальные права: SA узлов — только pull из реестра, SA CI — только push;
- [ ] сетевые политики (Calico) — **включаются только при создании кластера**;
- [ ] узлы без публичных IP + NAT; группы безопасности;
- [ ] статический IP для балансировщика (не меняется при пересоздании кластера);
- [ ] `terraform fmt`, `validate`, `providers lock -platform=linux_amd64 ...` (для CI).

```bash
terraform init -backend-config=backend.hcl
terraform plan -out=tfplan        # читать! ~ на месте, -/+ пересоздание, - удаление
terraform apply tfplan
terraform plan -detailed-exitcode # 0 = инфраструктура совпадает с кодом
```

!!! tip "Если apply долго «Still creating»"
    Смотри ресурс в самом облаке (`yc ... get`, `list-nodes`) — там настоящая ошибка
    (у нас — `RESOURCE_EXHAUSTED` по квоте), а Terraform просто ждёт.

**Готово, когда:** `plan` → `No changes`, узлы кластера `Ready`, `kubectl get pods -A` — всё `Running`.

## 6. Платформа кластера

Ставится **отдельно от приложения** (иначе каждый деплой приложения передеплоивает Prometheus).
Один идемпотентный скрипт или цель Makefile:

1. мониторинг (kube-prometheus-stack) — первым, он ставит CRD `ServiceMonitor`;
2. ingress-контроллер на статическом IP;
3. cert-manager — если есть домен;
4. обработчик прерываемых узлов — если узлы прерываемые;
5. namespace приложения + ServiceAccount для CI с правами **только в нём**.

```bash
kubectl auth can-i create deployments -n app --as=system:serviceaccount:app:ci   # yes
kubectl auth can-i get pods -n monitoring    --as=system:serviceaccount:app:ci   # no
```

**Готово, когда:** балансировщик получил IP, Grafana открывается, kubeconfig CI имеет права только
в namespace приложения.

## 7. Чарт и первый деплой — руками

Чек-лист Deployment:

- [ ] readiness и liveness (liveness **не проверяет зависимости**); startup — если долгий старт;
- [ ] requests и limits (без requests не работает HPA);
- [ ] `securityContext`: non-root, read-only FS, `drop: [ALL]`, seccomp;
- [ ] ≥ 2 реплики, PDB, `topologySpreadConstraints` (строгие, с `matchLabelKeys: [pod-template-hash]`);
- [ ] `replicas` не задавать при включённом HPA;
- [ ] `checksum/config` — перезапуск подов при смене ConfigMap/Secret;
- [ ] тег образа обязателен (`required`), без `latest`.

```bash
helm lint charts/app
helm template app charts/app | kubeconform -strict -summary -ignore-missing-schemas
helm upgrade --install app charts/app -n app --set image.tag=<sha> --wait --timeout 5m
kubectl -n app get pods -o wide            # Ready? на разных узлах?
curl -s http://<ip>/health
```

**Готово, когда:** приложение отвечает снаружи после **ручного** деплоя. Только после этого — CI.

## 8–9. CI/CD

Строй постепенно: сначала **build**, потом **test**, потом **release + deploy**.

| Стадия | Что | Проверка |
|---|---|---|
| build | образ `:<sha>` в реестр | образ виден в реестре |
| test | линтеры, тесты, сканер образа, `helm lint`, `terraform validate` | всё зелёное на ветке |
| release | только тег `vX.Y.Z`: перетегировать **тот же** образ (`crane tag`), чарт в OCI | теги в реестре |
| deploy | `helm upgrade --atomic --wait` + smoke-тест | откат при сломанной версии |

- [ ] переменные: Protected — только то, что нужно **тегу** (kubeconfig); то, что нужно веткам
  (реестр, ключ push), — без Protected;
- [ ] File-переменная — это **путь** к файлу (`cat "$VAR"`);
- [ ] авторизация в реестр без короткоживущих токенов (у Yandex: `json_key` + JSON ключа SA);
- [ ] `allow_failure` для необязательного (уведомления, аудит зависимостей);
- [ ] пайплайн, где остались только `.post`-задачи, не создаётся — проверяй ручным запуском.

**Готово, когда:** тег → релиз → деплой → приложение отвечает; намеренно сломанная версия
откатывается сама. Подробно — [Диплом: CI/CD](diploma-cicd.md).

## 10. Наблюдаемость

- [ ] метрики приложения собираются (`up{namespace="app"} == 1`);
- [ ] дашборд R.E.D.: Rate, Errors (по кодам ответа — из приложения или ingress), Duration (p50/p95/p99);
- [ ] дашборд в коде (JSON в репозитории, ConfigMap с меткой `grafana_dashboard`);
- [ ] алерты на SLO, с `for:`; проверены нагрузкой;
- [ ] лимиты памяти у компонентов мониторинга с запасом (Grafana на 256Mi у нас падала по OOM).

```bash
# дать трафик и посмотреть на графики
kubectl run load -n default --rm -it --image=williamyeh/hey -- -z 3m -c 50 http://<ip>/api/...
```

Подробно — [Диплом: мониторинг](diploma-monitoring.md).

## 11. Сдача и уборка

**README** — архитектура, ветвление и версионирование, пошаговое развёртывание с нуля, переменные,
результаты проверок. Проверка README: может ли другой человек поднять всё **только по нему**.

**Финальный чек-лист:**

- [ ] `terraform plan` → `No changes`;
- [ ] пайплайн по тегу зелёный от начала до конца;
- [ ] приложение отвечает снаружи;
- [ ] в git нет секретов (`git grep -nE "key|secret|password|token"` глазами);
- [ ] ресурсы, которые не нужны для проверки, погашены.

**Уборка — в обратном порядке** (иначе останутся «сироты», которые тратят деньги):

1. `helm uninstall` приложения, ingress, мониторинга — Kubernetes сам удалит балансировщики;
2. удалить PVC — облако удалит диски;
3. `terraform destroy -target=module.kubernetes` — кластер (сеть, реестр, IP остаются);
4. при полной уборке — очистить реестр от образов, затем `terraform destroy`;
5. проверить в облаке: ВМ, диски, балансировщики, IP — пусто.

## «Не работает» — где искать, по слоям

Идти **снизу**: если не работает слой N, бесполезно чинить N+1.

| Слой | Команда | Типичная причина |
|---|---|---|
| Облако | то же действие от владельца, `yc ... get`, квоты | биллинг, квоты |
| Terraform | `plan`, `state list`, `providers schema -json` | дрейф, deprecated, права SA |
| Узлы | `kubectl get nodes`, `describe node` | NotReady, нет CNI, давление ресурсов |
| Поды | `get pods` → `describe` (Events) → `logs --previous` | образ, пробы, ресурсы, OOM, PSA |
| Сеть | `kubectl run curl` изнутри, `curl -w '%{http_code}'` снаружи | NetworkPolicy, Ingress, Service selector |
| Метрики | `up{}`, список `__name__`, запрос в API Prometheus | ServiceMonitor не выбран, метрик нет |
| CI | лог задачи, флаги переменных, раннер, сеть раннера | Protected, недоступный внешний сервис |

Порядок по поду: **статус → Events → логи → `lastState.terminated.reason`**.
`Pending` — планирование, `CrashLoopBackOff` — приложение, `ImagePullBackOff` — образ/доступ,
`0/1 Running` — readiness. Все реальные случаи — [журнал проблем диплома](diploma-troubleshooting.md).

## Сколько это занимает

| Этап | Первый раз | С этой памяткой и готовым кодом |
|---|---|---|
| Разведка | полдня | 1 час |
| Образы | 1 день | 1–2 часа |
| Доступы, квоты, раннеры | от часа до дня (ожидание биллинга/квот) | 30 мин + ожидание |
| Terraform + кластер | 2–4 дня | 1 час (из них ~20 мин — создание кластера) |
| Платформа + чарт + первый деплой | 2–3 дня | 1 час |
| CI/CD | 2–3 дня | 1–2 часа отладки на новом раннере |
| Мониторинг | 1–2 дня | 30 мин |

Резерв закладывай не на код, а на **окружение**: доступы, квоты, сеть, чужие ограничения.
