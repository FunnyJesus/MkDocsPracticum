# Балансировка нагрузки (Load Balancing)

**Балансировка нагрузки** — распределение входящего трафика по нескольким серверам/репликам, чтобы ни один из них не перегружался, а система в целом оставалась доступной и отказоустойчивой.

> В этом проекте балансировщик уже встречался: `nginx` как мост между `frontend-net` и `backend-net` (см. [Сети в Docker Compose](compose-networks.md)). Здесь — общая теория и алгоритмы, которые за этим стоят.

## Зачем нужен балансировщик

* **Отказоустойчивость** — если один бэкенд умер, трафик уходит на живой.
* **Производительность** — нагрузка распределяется, каждый сервер нагружен равномерно.
* **Масштабирование** — добавлен ещё один экземпляр → балансировщик сразу начинает слать трафик на него.
* **Единая точка входа** — клиент знает один адрес (балансировщика), а не множество бэкендов.
* **SSL-терминация, кэширование, сжатие** — часто выполняются на балансировщике.

## Reverse proxy vs обычный (forward) proxy

| | Forward proxy | Reverse proxy |
|---|---|---|
| Для кого | Для клиентов: клиент идёт через прокси наружу | Для серверов: клиент идёт на прокси, тот распределяет по бэкендам |
| Кто «за спиной» | Интернет | Наши бэкенд-серверы |
| Зачем | Анонимность, обход ограничений, кэш | Балансировка, безопасность, скрытие внутренней структуры |
| Пример | corporate-прокси браузера | nginx/haproxy перед приложением |

**Балансировщик в наших конспектах — это reverse proxy**: он принимает запрос клиента и раздаёт его внутренним сервисам (`menu-service`, `order-service`), которых клиент напрямую не видит.

## Терминология

| Термин | Значение |
|---|---|
| **Backend / апстрим / upstream** | группа серверов, между которыми балансируется трафик |
| **Worker / реплика** | отдельный экземпляр приложения внутри upstream |
| **Health check** | периодическая проверка живости бэкенда (HTTP 200 / TCP / приложение) |
| **Session affinity / sticky sessions** | «прилипание» клиента к одному и тому же бэкенду |
| **Алгоритм балансировки** | правило, по которому выбирается следующий бэкенд |

## Алгоритмы балансировки (основные)

| Алгоритм | Принцип | Плюсы | Минусы | Когда брать |
|---|---|---|---|---|
| **Round Robin** | по кругу: 1→2→3→1→2… | простой, равномерно по очереди | не учитывает нагрузку/мощность | однородные серверы |
| **Weighted Round Robin** | Round Robin с весами (более мощный сервер — больше запросов) | учёт мощности | всё равно не смотрит на реальную нагрузку | серверы разной мощности |
| **Least Connections** | отдаём тому, у кого меньше всего активных соединений | учитывает реальную занятость | сложнее | запросы разной длительности |
| **IP Hash / Hashing** | хэш IP клиента → всегда один и тот же бэкенд | sticky без хранения состояния | неравномерно при малом числе клиентов | нужны sticky-сессии |
| **Least Response Time** | наименьшее время ответа + активные соединения | самый «умный» | требует сбора метрик | требовательные к задержке системы |

> Главная развилка: **Round Robin** — «поровну по очереди», **Least Connections** — «поровну по занятости». Для статичных однородных бэкендов хватает Round Robin; для запросов разной длительности лучше Least Connections.

## Примеры конфигов

### nginx: upstream + Round Robin (по умолчанию)

```nginx
http {
    # Группа бэкендов. Без директивы выбора алгоритма nginx берёт Round Robin.
    upstream menu_app {
        server menu-service:8000;
        server menu-service-2:8000 weight=2;   # более мощный — 2 «доли» трафика
        server menu-service-3:8000 down;        # временно исключён
    }

    server {
        listen 80;

        location /api/menu {
            proxy_pass http://menu_app;
        }
    }
}
```

* Алгоритм по умолчанию в nginx — **Round Robin**.
* Директива `weight=N` даёт weighted round robin.
* `down` — исключить сервер из балансировки (например, на время деплоя).

### nginx: Least Connections — `least_conn`

```nginx
upstream menu_app {
    least_conn;                     # включаем least connections
    server menu-service:8000;
    server menu-service-2:8000;
}
```

### nginx: IP Hash (sticky)

```nginx
upstream menu_app {
    ip_hash;                        # тот же клиент → тот же бэкенд
    server menu-service:8000;
    server menu-service-2:8000;
}
```

### nginx: health check

```nginx
upstream menu_app {
    server menu-service:8000;
    server menu-service-2:8000;
}
```

> В открытом nginx health check для upstream появился позже (в nginx plus он встроен). В Docker-сетях обычно хватает того, что nginx по умолчанию периодически проверяет серверы на ошибки соединения (fail_timeout / max_fails). Полноценный health check проще сделать через `haproxy` или `resolver`+переменные (см. [compose-networks.md](compose-networks.md)).

### haproxy: Round Robin и Least Connections

```haproxy
frontend http-in
    bind *:80
    default_backend menu_app

backend menu_app
    # balance roundrobin | leastconn | source (по IP клиента, sticky)
    balance roundrobin
    server menu-1 menu-service:8000 check
    server menu-2 menu-service-2:8000 check
```

* `balance roundrobin` — по кругу.
* `balance leastconn` — по наименьшему числу соединений.
* `balance source` — hash по IP клиента (sticky).
* `check` — haproxy сам периодически проверяет живость бэкенда.

## «Прилипание» (sticky sessions)

Иногда приложение хранит состояние сессии на конкретном сервере (корзина, логин). Тогда важно, чтобы **один и тот же клиент попадал на один и тот же бэкенд**:

* **Sticky cookie** — балансировщик ставит cookie, по которому помнит, куда отправил клиента.
* **IP hash / source** — вычисляет бэкенд из IP клиента.
* **Session store** (Redis и т.п.) — выносит сессию в общее хранилище, тогда sticky вообще не нужен.

> Современный подход — **не «прилипать», а выносить состояние наружу** (Redis/БД). Тогда любая реплика обрабатывает любой запрос, и масштабирование/отказы становятся тривиальными. Sticky оставляют только там, где переезд состояния невозможен.

## Балансировка на разных уровнях

| Уровень | Инструменты | Что балансируют |
|---|---|---|
| Один хост / Docker Compose | nginx, haproxy (reverse proxy) | HTTP-запросы между контейнерами |
| Kubernetes | Service (ClusterIP/LoadBalancer/NodePort), Ingress | поды по меткам |
| Облако | Yandex LB, AWS ELB/ALB, GCP LB | трафик между ВМ/подсетями |
| L4 vs L7 | TCP (L4) / HTTP (L7) | транспортный vs прикладной уровень |

> **L4** балансирует по IP/порту (быстро, но «не видит» HTTP). **L7** понимает HTTP/HTTPS и умеет маршрутизировать по URL, заголовкам, cookie (это уже территория nginx/Ingress).

## Частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Sticky-сессия ломается, корзина пропадает | Round Robin без sticky отправляет на разные реплики | `ip_hash` / `balance source` / sticky cookie, либо внешний session store |
| Один бэкенд перегружен | Round Robin не смотрит на занятость | перейти на least connections |
| Новые реплики не подхватываются | статический `proxy_pass` + резолв раз при старте | переменная + `resolver` (см. [compose-networks](compose-networks.md)) |
| Запросы идут на мёртвый сервер | нет health check | включить `check` в haproxy / `max_fails` в nginx |
| Backend 502 после добавления реплики | имя сервиса не резолвится в общей сети | проверить сети и имя (см. [Сети в Docker Compose](compose-networks.md)) |

## Best Practices

* **Начинайте с Round Robin.** Для однородных серверов этого достаточно, алгоритм предсказуем.
* **Разные длительности запросов → Least Connections.**
* **Нужна sticky — предпочитайте sticky cookie, а не IP-hash** (IP может меняться / несколько клиентов за одним NAT).
* **Не забывайте про health check** — иначе трафик уходит в «мёртвые» бэкенды.
* **Состояние — наружу** (Redis/БД), тогда sticky не нужен и всё масштабируется.
* **Держите балансировщик доступным снаружи, а бэкенды — в приватной сети** (как `nginx` в [compose-networks.md](compose-networks.md)).
