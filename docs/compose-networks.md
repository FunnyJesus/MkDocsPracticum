# Сети в Docker Compose

Сети в Docker — механизм **изоляции и связывания** контейнеров. В Compose сети объявляются на верхнем уровне (`networks:`) и подключаются к сервисам через ключ `networks:` (множественное число!) внутри сервиса.

> Практический пример — «Galactic Pizza»: `frontend` живёт в отдельной сети `frontend-net`, а `menu-service`, `order-service` и `redis` — в `backend-net`. Балансировщик `nginx` соединяет обе сети.

## Зачем нужны сети

* **Внутренний DNS по имени сервиса.** Внутри одной сети контейнеры обращаются друг к другу по имени сервиса из compose (`menu-service`, `redis`), а не по IP.
* **Изоляция.** Сервисы в разных сетях не видят друг друга. Можно ограничить, кто с кем общается («не взаимодействующие сервисы не должны видеть друг друга»).
* **Безопасность и порядок.** Не выставляешь лишние порты наружу, контролируешь границы.

## Объявление и подключение

На верхнем уровне объявляем сети:
```yaml
networks:
  backend-net: {}
  frontend-net: {}
```

Подключаем к сервису (имя ключа — `networks`, не `network`):
```yaml
redis:
  networks:
    - backend-net

frontend:
  networks:
    - frontend-net
```

Сервис можно подключить сразу к нескольким сетям — так работает `nginx`, мост между `backend-net` и `frontend-net`:
```yaml
nginx:
  networks:
    - backend-net
    - frontend-net
```

## Два подхода к объявлению сетей

### 1. Дефолтная сеть (если ничего не указывать)

Если у сервиса **нет** `networks:` (и `network_mode`), Compose помещает его в **дефолтную сеть проекта**. Это удобно для простых проектов, но даёт «все со всеми» без изоляции.

### 2. Явные сети (рекомендуется)

Объявляем сети сам и привязываем сервисы. Включается **изоляция**: например, `frontend` изолирован от `redis`, `menu`, `order`.

> Важный нюанс: если смешивать явные сети (`networks:`) у одних сервисов и дефолтную у других, они могут оказаться **в разных сетях** и не увидеть друг друга по имени. Если задаёшь сети — задавай их **всем** сервисам, которые должны взаимодействовать.

## Изоляция frontend в Galactic Pizza

Требование задания: «сервис frontend изолирован от остальных сервисов, кроме nginx».

```yaml
services:
  frontend:
    networks:
      - frontend-net     # frontend видит только то, что в этой сети — то есть nginx

  nginx:
    networks:
      - backend-net      # nginx видит menu/order/redis
      - frontend-net     # и frontend

  menu-service:
    networks:
      - backend-net
  order-service:
    networks:
      - backend-net
  redis:
    networks:
      - backend-net
```

Итог: `frontend` физически не может обратиться напрямую к `menu-service` или `redis` — у них нет общей сети. Весь трафик frontend идёт только через `nginx`.

## Внутренний DNS и имена сервисов

Внутри сети каждый контейнер доступен по **имени сервиса** (из `services:`) и по имени контейнера.

```
menu-service  → разрешается в IP реплики menu
order-service → разрешается в IP реплики order
redis         → разрешается в IP redis
frontend      → разрешается в IP frontend
```

Поэтому в коде/конфигах ссылаются по имени:
```yaml
# menu-service ходит в order-service
- ORDER_SERVICE_URL=http://order-service:8001

# order-service ходит в menu-service
- MENU_SERVICE_URL=http://menu-service:8000
```

> Это работает только внутри **одной сети**. Если два сервиса в разных сетях — обращение по имени не сработает.

## DNS и масштабирование: почему статический proxy_pass «залипает»

Это ключевая тема связки «сети + балансировка + реплики».

Docker встроенный DNS-сервер живёт по адресу **`127.0.0.11`** в каждом контейнере. Когда у сервиса несколько реплик, имя `menu-service` резолвится в **несколько IP**.

**Проблема nginx:** если написать `proxy_pass http://menu-service:8000;` (статическое имя), nginx резолвит DNS **один раз при старте** и запоминает полученные IP. При изменении числа реплик (добавили/убрали контейнеры → у них новые IP) nginx **не узнает** об этом, пока не перезапущен.

### Решение: динамический DNS-резолвинг через переменную + resolver

```nginx
http {
    resolver 127.0.0.11 valid=10s;   # резолвим через Docker DNS, обновляем каждые 10с

    server {
        listen 80;

        location /api/menu {
            set $menu_backend http://menu-service:8000;   # переменная!
            proxy_pass $menu_backend;                     # резолв на каждый запрос
        }
    }
}
```

Когда `proxy_pass` содержит **переменную**, nginx резолвит имя через `resolver` на каждый запрос (с TTL-кэшем `valid`). Поэтому изменение числа реплик подхватывается **автоматически, без рестарта nginx**.

### Отличие статического upstream от переменной

| Форма | Балансировка на N реплик | Подхват новых реплик без рестарта |
|---|:--:|:--:|
| `proxy_pass http://svc:port;` (статическое имя) | ✅ | ❌ |
| `proxy_pass http://backend;` (upstream с `server svc;`) | ✅ | ❌ (резолв один раз) |
| `set $b http://svc:port; proxy_pass $b;` + `resolver` | ✅ | ✅ |

> Вариант с `upstream` + `zone` + `server svc resolve;` тоже даёт динамику, но сложнее и требует shared memory zone. Для простых проектов достаточно переменной + `resolver`.

### Нюанс: resolver 127.0.0.11 работает в кастомных сетях

DNS-сервер `127.0.0.11` доступен в контейнере **только если сервис подключён к пользовательской (bridge) сети**. В дефолтном bridge он не работает. Раз мы объявляем кастомные сети `backend-net`/`frontend-net` — `resolver 127.0.0.11` корректен.

### Передача URI при переменной

Если в `proxy_pass` переменная **без** URI-части (`http://хост:порт` — без слэша и пути), nginx передаёт бэкенду **тот же URI, что пришёл в location**:

```nginx
location /api/menu {
    set $menu_backend http://menu-service:8000;
    proxy_pass $menu_backend;   # /api/menu/popular → на menu-service уйдёт /api/menu/popular
}
```

Никаких `rewrite` для базовой маршрутизации не нужно.

## Драйверы сетей (кратко)

| Драйвер | Что это | Когда использовать |
|---|---|---|
| `bridge` | Изолированная NAT-сеть на хосте (по умолчанию в Compose) | Стандартный случай для мульти-контейнерного приложения |
| `host` | Контейнер делит сетевой стек с хостом | Когда нужен прямой доступ к портам хоста (редко, для производительности) |
| `overlay` | Сеть между нодами в Swarm | Только в Docker Swarm кластере |
| `none` | Без сети | Для полностью изолированных задач |

Практически всегда в Compose достаточно `bridge` (по умолчанию).

## Полный пример сетей в Galactic Pizza

```yaml
services:
  redis:
    networks: [backend-net]
  menu-service:
    networks: [backend-net]
  order-service:
    networks: [backend-net]
  frontend:
    networks: [frontend-net]
  nginx:
    networks: [backend-net, frontend-net]

networks:
  backend-net: {}
  frontend-net: {}
```

## Частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Сервисы не видят друг друга по имени | Один в `backend-net`, другой в дефолтной сети | Подключить обоих к одной сети |
| `additional properties 'network' not allowed` | `network:` вместо `networks:` | Исправить ключ на `networks:` |
| nginx не подхватывает новые реплики | Статический `proxy_pass` + резолв при старте | Перейти на переменную + `resolver 127.0.0.11` |
| nginx отдаёт 502 | Имя в `proxy_pass` не существует / сервис в другой сети | Проверить имя сервиса и общую сеть |

## Best Practices

* **Объявляйте сети явно** и привязывайте сервисы — так проще контролировать изоляцию.
* **Изолируйте frontend/внешний контур** от внутренних сервисов (как frontend в `frontend-net`).
* **Для балансировщика** (nginx) используйте `proxy_pass` с переменной + `resolver 127.0.0.11`, чтобы масштабирование работало без рестарта.
* **Держите сервисы, которые общаются, в одной сети**, чтобы работал внутренний DNS по именам.
