# Continuous Delivery / Deployment (теория)

**CD** — расширение CI, которое автоматизирует доставку и/или развёртывание приложения в окружения. Это «последняя миля» пайплайна: от готового артефакта до работающего сервиса.

> Три уровня зрелости:

> 1. **Continuous Integration (CI)** — авт. сборка и тесты при каждом коммите. 

> 2. **Continuous Delivery (CD)** — артефакт всегда готов к выкатке, деплой в prod — по нажатию кнопки (ручной триггер).

> 3. **Continuous Deployment (CD)** — деплой в prod происходит автоматически, без ручного действия.

## Continuous Integration vs Continuous Delivery vs Continuous Deployment

| Характеристика | CI | Continuous Delivery | Continuous Deployment |
|---|---|---|---|
| Сборка/тесты | ✅ авто | ✅ авто | ✅ авто |
| Артефакт готов | ✅ | ✅ | ✅ |
| Деплой в staging | — | ✅ авто | ✅ авто |
| Деплой в production | — | ручная кнопка | ✅ авто |
| Роль человека | нет | «нажать кнопку» | минимальна |

**Continuous Delivery** — это «вы всегда можете выкатить», **Continuous Deployment** — «вы всегда выкатываете».

## Почему CD важен

* **Быстрее доставка фич** — код попадает в прод за минуты, а не недели.
* **Меньше рисков** — маленькие частые изменения проще откатить, чем большие редкие.
* **Однообразие процесса** — деплой через пайплайн, а не «руками по чек-листу».
* **Обратная связь** — быстрее узнаёшь, что что-то сломалось (мониторинг + автоматический откат).
* **Автоматизация рутины** — не нужно руками выполнять повторяющиеся шаги деплоя.

## Пайплайн CD (классика)

```
build → test → package → deploy(staging) → e2e → approve → deploy(prod) → smoke
```

1. **Build** — собрать артефакт (jar, image)
2. **Test** — юнит/интеграционные тесты
3. **Package** — упаковать (Docker-образ, задеплоить в registry)
4. **Deploy → staging** — выкатить в тестовое окружение
5. **E2E / дымовые тесты** — проверить интеграцию
6. **Approve** — подтверждение на выкатку в прод (manual)
7. **Deploy → prod** — выкатить в боевое окружение
8. **Smoke / откат** — быстрая проверка + план отката (rollback)

## Артефакты и реестры

* **Артефакт** — результат сборки: бинарник, jar, Docker-образ, Helm-чарт.
* **Container Registry** — хранилище образов (Docker Hub, GitLab Container Registry, Yandex Container Registry). Образы версионируются **тегами** (`myapp:1.2.3`, `myapp:latest`, `myapp:sha-<hash>`).
* **Версионирование** — immutable-версии (`1.2.3`) для воспроизводимости, а не перезапись `latest`.

## Окружения (environments)

* **dev** — разработка
* **staging / preprod** — максимально близко к проду, здесь гоняют e2e
* **production** — боевое

Правило: staging должен быть как можно ближе к prod (тот же способ деплоя, те же конфиги), чтобы ловить проблемы до выкатки.

## Откат (rollback)

Всегда должен быть план отката. Варианты:
* **Деploy предыдущей версии** — вернуть старый артефакт.
* **Использовать immutable-теги** — знаешь, какая версия была.
* **Использовать стратегию деплоя**, которая позволяет откатиться без даунтайма (см. стратегии).

## Связь с оркестрацией

CD часто «выкатывается» не на голые сервера, а в **оркестраторы**: Docker Compose, Kubernetes, облачные сервисы. Пайплайн CD подготавливает артефакт, а инструмент деплоя раскатывает его по репликам.
